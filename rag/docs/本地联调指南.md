# 本地 RabbitMQ 联调指南

以下命令在 `rag/` 执行。可使用 README 的 Compose 同时启动 RabbitMQ、Redis、Chroma，也可使用现有服务并修改 `.env`。默认 Redis 16379、Chroma 8002、RabbitMQ 5672；管理界面为 `http://127.0.0.1:15672`，示例账号 `rag / rag-local-password`。单节点 Compose 用于本地恢复演示，不代表多节点高可用。

如果使用你已安装的 RabbitMQ，在 `rag/.env` 中配置以下地址；此时只需用 `docker compose up -d redis chroma` 启动另外两个依赖，避免再次占用 RabbitMQ 端口。然后填写 `DASHSCOPE_API_KEY`，分别运行消费者与 API：

```dotenv
RABBITMQ_URL=amqp://guest:guest@localhost:5672/%2F
```

`%2F` 表示虚拟主机 `/`。本地 `.env` 不进入 Git；`.env.example` 中保留与 Compose 一致的演示账号。

## 1. 模拟知识库操作

默认 `RAG_OBJECT_SOURCE=local`。脚本先把文件放入不可变对象路径模拟 OSS，再发送持久 MQ 事件。请使用自己的 PDF、Markdown 或 UTF-8 文本文件。

```powershell
uv run --project rag_api_service python scripts/publish_event.py create --document-id oa-policy --version 1 --file "D:\your-files\制度.pdf"
uv run --project rag_api_service python scripts/publish_event.py update --document-id oa-policy --version 2 --file "D:\your-files\制度修订.pdf"
uv run --project rag_api_service python scripts/publish_event.py delete --document-id oa-policy --version 3
uv run --project rag_api_service python scripts/ingestion_admin.py jobs
```

`document_id` 稳定不变，版本递增，删除也递增。不要用文件名判断文档身份。跨租户/知识库时增加 `--tenant-id`、`--knowledge-base-id`；默认均为 `default`。

每次发送先输出并保存 `event_file`，若发布未被确认，可用同一 JSON 重放，保持相同 `event_id`：

```powershell
uv run --project rag_api_service python scripts/publish_event.py replay --event-file "<上一步输出的 event_file>"
```

`--prepare-only` 可只生成事件和模拟对象，不连接 RabbitMQ。脚本模拟的是生产者，不包含知识库项目的业务数据库事务 Outbox。实际接入时，知识库应在业务事务内写文件版本和 Outbox，再用 mandatory、持久消息与 Publisher Confirms 投递。

## 2. 查询和查看任务

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8011/api/docs/query -ContentType 'application/json; charset=utf-8' -Body '{"query":"请假如何审批？","tenant_id":"default","knowledge_base_id":"default"}'
Invoke-RestMethod http://127.0.0.1:8011/api/docs/ingestion/jobs
```

`pending → processing → succeeded` 表示正常执行；临时错误变为 `retry`，重试耗尽变为 `dead`，过期版本变为 `superseded`。MQ ACK 发生在 Inbox 持久落盘后，只表示可靠接收，不代表索引完成。收到 Publisher Confirm 更不代表索引完成。

查询返回 `answer`、结构化 `sources` 与 `snapshot_id`。来源包含文档 ID、文档版本、chunk ID、对象位置、内容和分数。MCP 工具 `query_rag` 接收 query 和 knowledge_base_id，租户来自 MCP 配置 `RAG_TENANT_ID`。

设置 `RAG_SERVICE_TOKEN` 后，API 请求需增加 `Authorization: Bearer <token>`；MCP 会自动携带。该令牌是服务间认证。真实多租户接入还需要网关/业务服务校验用户权限，不能把请求体 tenant_id 当作已授权身份。

## 3. 事件协议与 OSS

新增和更新示例：

```json
{
  "schema_version": 1,
  "event_id": "6aaec657-04d0-465d-9657-c54260892be0",
  "event_type": "document.updated",
  "tenant_id": "company-a",
  "knowledge_base_id": "oa-policy",
  "document_id": "doc-1001",
  "document_version": 7,
  "file_name": "报销制度.pdf",
  "trace_id": "request-123",
  "object": {
    "bucket": "company-knowledge",
    "key": "documents/doc-1001/v7/policy.pdf",
    "sha256": "<文件内容的64位小写SHA-256>",
    "version_id": "<开启OSS版本控制时的可选版本ID>"
  }
}
```

`event_type` 支持 `document.created`、`document.updated`、`document.deleted`。删除只需身份字段和更高版本，必须省略 object，文件名可省略。ID 字段使用 1–128 位字母、数字、下划线、点、冒号或短横线，首位是字母或数字。

`document_version` 是知识库业务侧的递增正整数，不使用时间戳或 OSS versionId 排序。允许版本有间隔，每个新增/更新事件指向一份完整文件。相同 event_id 不同语义内容、同文档同版本不同内容都会被隔离；trace 和时间不影响幂等指纹。

OSS 必须使用明确 version_id 或不可变对象 key，并提供 SHA-256。对象被错误覆盖时，校验失败，不会把新文件冒充旧版本入库。设置 `RAG_OBJECT_SOURCE=oss`、`OSS_ENDPOINT`、`OSS_BUCKET` 和环境凭证（支持临时凭证）；`OSS_KEY_PREFIX` 可限制对象范围。准备真实 JSON 后用 replay 发布即可。

目录移动、重命名不改变 document_id。若名称变化需要进入来源元数据，应发布该文档的新完整版本。单独的目录权限事件不在此版协议内。

## 4. 失败恢复演示

| 操作 | 预期结果 |
|---|---|
| 同一事件 JSON 发布两次 | 只有一个任务，无重复发布 |
| 先发 v3，再发 v2 | v2 为 superseded |
| 删除 v4 后重放旧更新 | 墓碑阻止旧文档复活 |
| 暂停 Redis/Chroma，再发更新 | retry，旧快照继续可查询；恢复依赖后重试 |
| 处理中结束 Worker，再启动 | 恢复 processing，尝试次数不丢失 |
| 修改 JSON 中 SHA-256 后发布新版本 | dead，旧快照不被替换 |
| 停止 RabbitMQ 的死信发布连接 | 待发送死信保留在 SQL Outbox，恢复后重发 |

查看和重试：

```powershell
uv run --project rag_api_service python scripts/ingestion_admin.py dead
uv run --project rag_api_service python scripts/ingestion_admin.py retry --event-id "<dead任务的原event_id>"
```

`dead` 命令展示尚未确认送达 MQ 的死信；全部失败任务通过 jobs 查看。修复临时环境故障后，人工 retry 保持原事件和文档版本。已有更高版本时拒绝重试旧版本。原文件/事件内容错误时由知识库发正确的新版本，不能篡改旧事件。普通 replay 用于验证幂等，不会自动复活 dead 任务。

MQ 到 Inbox、死信 Outbox 到 MQ 都存在可能重复的崩溃窗口，所以保证是至少一次与幂等效果，不是跨存储 exactly-once。

## 5. 新旧存储路径

事件路径：LlamaIndex Pipeline 做纯解析切分，MarkdownNodeParser → SentenceSplitter（默认 512/50），不在暂存时删旧文档。没有使用会增加额外模型请求的 TitleExtractor。向量按精确输入、模型/修订、维度、管道版本、租户知识库缓存到持久任务库；Redis 保存 generation 节点镜像及索引结构。

原 HTTP 路径仍保留 Redis IngestionCache，需设置 `RAG_INGESTION_MODE=legacy`。事件模式默认启用，拒绝旧上传、直接删除、重置和在线修改切分参数，避免绕过版本协议。原有数据不会自动混入事件集合，需重新发布初始文档版本。

全文重新解析不等于重新生成全部向量；只有实际 Embedding 输入一致的 chunk 才复用。PDF 重排可能改变切分边界，因此不承诺只处理编辑过的一小段。新路径 BM25 使用 jieba，融合为 dist_based_score，关闭问题扩写；本次没有重新测量历史 80 题成绩。

模型或维度变更属于知识库迁移，应使用新集合和完整重建。本版禁止发布混合向量空间的快照，查询配置与快照模型不符会返回不可用，不能直接热换配置后继续查旧向量。

本版为单机、单索引写入者，用 OS 文件锁避免两个 Worker 同时发布。API 和 Worker 共享同一持久化目录。SQLite 不适用于 NFS 或多机调度；扩容要换为 MySQL/PostgreSQL、带 fencing 的任务认领以及共享快照存储。

旧快照、旧向量和失败 generation 暂不自动回收，磁盘会增长。生产回收需要读者租约和保留期，不能在新版本发布后立刻删除旧版本。应备份 Inbox、快照、向量存储，不能只备份 Redis。

## 6. 测试

从仓库根目录运行：

```powershell
uv run --project rag/rag_api_service python -m unittest discover -s rag/tests -v
```

包含状态机、故障注入、实际 LlamaIndex 切分、jieba BM25、Chroma 预过滤和 API 测试，不调用付费模型。真实 RabbitMQ 集成测试需先部署 RabbitMQ 4，并设置 `RAG_TEST_RABBITMQ_URL` 后运行相同命令；未设置时明确跳过。真实 OSS、Redis 服务和模型端到端联调需要自己的环境配置。

```powershell
$env:RAG_TEST_RABBITMQ_URL='amqp://guest:guest@localhost:5672/%2F'
uv run --project rag/rag_api_service python -m unittest discover -s rag/tests -v
```

2026-10-24 本机验证：42 项测试全部通过，包含 3 项真实 RabbitMQ 测试：重复消息去重、未 ACK 断线重投，以及新增 → 修改 → 删除 → 旧版本重放。最后一项使用实际 LlamaIndex 解析、本地 Chroma 和 jieba BM25；Embedding 使用固定测试向量，Redis 镜像使用替身，因此该结果不代表真实 OSS、Redis 或付费模型的端到端验证，也不是检索效果评测。测试只创建并删除带随机后缀的独立测试队列。
