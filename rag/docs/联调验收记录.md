| 验证层次 | 实际验证的行为 |
|---|---|
| 真实 RabbitMQ | 发布确认、重复事件去重、未 ACK 断线重投 |
| 真实消息与索引流程 | 新增、修改、删除、旧版本重放；实际 LlamaIndex 解析、Chroma 节点写入、jieba BM25 构建与查询 |

Embedding 在测试中采用固定向量，Redis 镜像使用替身。未调用付费模型，也未使用实际 OSS、Redis 完成端到端联调。以上验证说明消费和发布机制，不提供检索准确率、召回率结论。

## 独立审查与修复

已完成一次独立上下文的代码审查；初始审查实例未成功启动，更换实例后完成。没有发现需要阻止提交的 Critical 问题；两项 Important 问题及另外两项调度/文档问题均已处理。

1. 数据库临时故障后，首次恢复失败会使任务一直停在 processing。改为保留 recovery_needed，恢复事务成功前不再认领任务。实际 Inbox SQL 回归测试先复现失败，再验证成功，无需重启进程。
2. JSON 转义的孤立 Unicode 代理字符可绕过原校验，导致无限重投。解析阶段增加 UTF-8 可编码性检查；文件名、对象 key、trace 字符串均验证先持久隔离再 ACK。回归测试先失败后通过。
3. 新任务的 next_at=0 会持续排在到期重试前。按实际效果将调度问题提升为应修复项，改为对已到期任务按接收顺序认领。回归测试验证旧重试先于新任务，先失败后通过。
4. 将“Chroma 停机仍可查询”的描述更正为“旧快照保持发布状态，查询依赖 Chroma 恢复”。Redis 镜像不可用时，既有查询不依赖 Redis。该项通过核对查询路径修正文档。

未留下待处理的审查小项。修复后重新运行完整测试。

## 实施决定与验证边界

- 按用户要求直接实现，以独立本地副本隔离开发，Agent 基线取自原目录已提交的 develop；原目录未提交改动未包含在本分支，避免混入其他任务。
- 旧实现保留为显式 legacy 模式，本次审查聚焦新事件链路，不替旧实现背书；选择 legacy 时仍需单独验证。
- OSS、真实模型和 Redis 的接口已实现，依赖版本与构造接口已检查；缺少实际端到端环境验证时，不宣称已验证其线上行为。
- 测试验证进程崩溃与持久事务恢复，不能证明硬件断电、存储设备或 Windows 目录重命名的全部持久性保证。真实部署应按文件系统和存储保证验收并备份。
- 本版为单机单索引写入者，旧 generation 暂不回收，终端用户的租户权限由上游认证服务负责；多机部署、无限期运行的磁盘容量管理和用户授权不能直接套用本地示例。
- 本次没有运行历史 80 题效果评测；固定向量验证流程，不支持对检索质量作新结论。

部署和模拟操作见 [本地联调指南](本地联调指南.md)，方案理由见 [可靠消费设计](可靠消费设计.md)。
