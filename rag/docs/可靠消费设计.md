# 知识库事件驱动 RAG：可靠消费与版本发布

知识库项目负责目录、文件元数据和 OSS；RAG 不根据文件名识别文档，也不监听 OSS 原生通知。知识库为每个文档维护递增整数版本，新增、修改、删除都递增，删除后保留版本墓碑。

## 方案与范围

采用“整篇文档重新解析和切分、相同 Embedding 输入复用向量、新版本完整后发布”。不重建其他文档的向量；BM25 在此规模下按知识库完整构建快照。原地修改 chunk 容易在 PDF 重排、切分边界移动和处理中断时暴露半份文档；先删旧再建会造成查询中断。

本版面向本地部署：RabbitMQ 4、单台 RAG Worker、SQLite WAL 持久化任务库、共享快照目录、Chroma Server、Redis。消费线程和索引线程分离；进程文件锁保证同一个任务库只有一个索引写入者。API 和 Worker 必须使用相同任务库与快照目录。不要把 SQLite 放在网络文件系统或多台机器上；多机部署需替换为 PostgreSQL/MySQL 的任务认领与版本 CAS，并将快照放到共享对象存储。

## 可靠性边界

1. 知识库服务在业务数据库事务里同时写文件记录和 Outbox。OSS 上传先完成，再提交文件版本和 Outbox；孤立对象另行清理。Outbox 发布使用持久消息、mandatory 和 Publisher Confirms，确认后标记已发送。模拟发送脚本只验证消费端，不声称实现了知识库的业务事务。
2. RabbitMQ 手动 ACK；消息先原子写入本地 Inbox，落盘成功才 ACK。这里 ACK 表示“RAG 已持久接收任务”，**不表示索引已完成**。索引成功另有 succeeded 状态。这样长时间解析和模型请求不占用 RabbitMQ 的未确认窗口。
3. Inbox 持久记录事件、语义指纹、尝试次数、下次执行时间、错误类型。事件 ID 去重，文档版本防乱序；同版本不同内容属于冲突，进入隔离记录。无效消息也先持久化隔离，再 ACK。
4. 任务先记 processing 和尝试次数，再执行。重启后恢复中断任务；指数退避加抖动，达到上限进入 dead。重试由本地任务调度实现，不依赖普通 TTL 死信转发的可靠性。其他文档可以继续处理。
5. dead 与待发布的死信记录同事务保存。转发到 RabbitMQ 死信队列时先取得 Publisher Confirm 再标记已发送。崩溃窗口可能重复投递，所以整体保证是至少一次和幂等效果，不是 exactly-once。

RabbitMQ 使用持久化 quorum 队列。消费队列禁用 broker 自动 delivery-limit 丢弃，由 Inbox 的持久尝试次数控制业务重试。数据库不可用时不 ACK，断开后交由 RabbitMQ 重投。

## 文档版本和查询一致性

每个节点 ID 由文档身份、版本、管道版本、序号决定；向量写入使用 upsert。缓存键包括租户、知识库、精确 Embedding 输入、模型名、维度、模型修订和管道版本，文件名、上传时间、版本号不进入 Embedding 输入。

新节点写入独立 generation；Redis 镜像与 Chroma 节点数量验证完成后，用“当前已发布文档集合 + 本次替换/删除”构建新的 BM25 和节点快照。写完不可变快照后，在 SQLite 事务中再次检查 desired_version，再同时切换知识库快照指针、文档活动版本和任务成功状态。

查询只读取一次快照指针：向量检索在 Chroma 查询之前按活动 generation 过滤，BM25 读取同一快照。不能先取向量 TopK 再丢弃旧版本，否则旧节点会挤占召回名额。删除发布后，快照不再含该文档；旧消息不能覆盖删除墓碑。旧快照和旧向量本版保留，避免影响进行中的查询；生产环境按查询租约和保留期做垃圾回收。

100 个 chunk 的第 21 个失败：任务进入 retry，活动快照仍指向原版本；前 20 个已缓存向量可复用，新版本整体不对查询可见。全部失败同样不发布。若发布成功后 ACK/进程中断，已持久化的任务状态保证恢复时不重复发布。由于 ACK 在 Inbox 落盘之后，这里准确的崩溃窗口是“发布完成但 Worker 尚未返回”，不是“发布完成后才 ACK”。

## 运行与验收

提供 local 对象源模拟 OSS 的不可变文件版本，也提供 oss2 下载适配器。下载必须校验 SHA-256，限制大小和本地路径范围。删除事件不需要源文件。事件模式拒绝旧上传/删除/重置接口绕过版本协议；旧 HTTP 模式可显式开启，旧数据不会自动混入新集合。

验收覆盖：重复事件、同版本冲突、乱序、删除墓碑、中断恢复、重试耗尽、死信发布失败、新版本部分失败、BM25 失败、发布前被更新版本抢先、向量复用、同一快照过滤。真实 RabbitMQ/OSS/模型联调与不依赖外部服务的故障测试分别报告。

参考：[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)、[Quorum 队列与死信可靠性](https://www.rabbitmq.com/docs/quorum-queues)。
