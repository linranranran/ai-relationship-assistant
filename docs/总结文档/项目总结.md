

# Day1-2026-9-22日

## sanitize_model_tool_calls函数是干嘛的？

`sanitize_model_tool_calls()` 是大模型输出和真实 Tool 执行之间的一道“安全检查门”。

大模型生成的 Tool 调用不能直接执行。这个函数负责把模型输出的计划检查、清洗并转换成系统能够信任的调用计划。

例如，大模型可能输出：

```
[
    {
        "tool": "delete_person",
        "args": {
            "person_id": "p_123",
            "owner_id": "别人的用户ID",
            "confirmed": True
        }
    }
]
```

如果直接执行，就会出现两个严重问题：

- 模型可以指定其他用户的 `owner_id`，造成越权访问。
- 模型可以自己生成 `confirmed=True`，绕过人工确认。

所以这个函数会把危险参数删除，得到：

```
[
    {
        "tool": "delete_person",
        "args": {
            "person_id": "p_123"
        }
    }
]
```

后面系统会：

1. 从登录令牌中注入可信的 `owner_id`。
2. 进入 `request_confirmation` 节点。
3. 用户明确确认后，由服务端注入 `confirmed=True`。
4. 最后才执行 `delete_person`。

## 它处在什么位置

完整链路是：

```
用户输入
   ↓
大模型规划 Tool
   ↓
sanitize_model_tool_calls
   ↓
风险判断
   ├─ 普通操作 → execute_tools
   └─ 删除操作 → interrupt → 用户确认 → execute_tools
```

大模型的输出属于“不可信输入”，性质上和前端参数相似。即使 Prompt 明确告诉模型不要输出某些字段，也不能保证模型永远遵守。

## 它干了什么

1. 确认最外层是列表
2. 过滤格式错误的调用

3. 保证 `args` 是字典

4. 删除模型无权控制的字段

5. 校验 Tool 参数

6. 拒绝未知 Tool

7. 生成 `call_id`

   一次任务里可能存在多个 Tool 调用：

   ```
   [
       {
           "tool": "find_person",
           "args": {"query": "张三"}
       },
       {
           "tool": "delete_person",
           "args": {"person_id": "p_123"}
       }
   ]
   ```

   清洗后，可以为每个调用生成唯一 ID：

   ```
   {
       "call_id": "call_abc123",
       "tool": "delete_person",
       "args": {
           "person_id": "p_123"
       }
   }
   ```

   它主要解决重复执行问题。

   例如：

   ```
   1. 用户点击“确认删除”
   2. 后端成功删除张三
   3. 网络在返回响应时中断
   4. 前端认为请求失败，再次发送恢复请求
   5. 后端第二次执行删除
   ```

   有了 `call_id`，执行 Tool 前可以查询执行记录：

   ```
   record = find_execution_record(call_id)

   if record and record.status == "SUCCESS":
       return record.result
   ```

   这样同一个调用即使收到两次，也只真正执行一次。

   它还可以用于审计：

   ```
   operation_id: op_001
   call_id: call_002
   owner_id: user_123
   tool: delete_person
   status: SUCCESS
   confirmed_by_user: true
   executed_at: 2026-09-22 15:20:00
   ```

   其中：

   - `operation_id` 表示一整次用户操作。
   - `call_id` 表示这次操作中的某一个 Tool 调用。

   例如：

   ```
   operation_id = 删除张三这项任务

   call_1 = 查询张三
   call_2 = 查询张三关联关系
   call_3 = 删除张三
   call_4 = 删除张三的向量数据
   ```

## 它解决的核心场景

这个函数主要解决四类问题：

1. **模型输出不稳定**

   模型可能缺少字段、给错类型或者输出不存在的 Tool。

2. **权限越界**

   模型可能生成其他用户的 `owner_id`，因此身份字段必须由服务端注入。

3. **绕过人工确认**

   模型可能根据用户对话自行推测“用户已经同意”，但只有 `/resume` 接口才能代表结构化确认。

4. **重复执行**

   网络重试、服务恢复或前端重复点击都可能让写操作执行两次，所以每个调用需要稳定的 `call_id`。

你可以把这个函数理解为：

```
大模型生成的是“执行建议”
sanitize_model_tool_calls 输出的是“通过系统检查的执行计划”
```

它不是普通的数据格式化函数，而是 Agent 从“能调用工具”走向“可靠调用工具”的关键边界。

## Pydantic是干什么的

你在 Java 里其实天天用这套东西，只是叫法不同：

| Python / Pydantic              | Java 对应物                                          |
| :----------------------------- | :--------------------------------------------------- |
| `class XxxArgs(BaseModel)`     | DTO / POJO                                           |
| 字段类型注解 `name: str`       | `private String name;`                               |
| `Field(ge=0, le=150)`          | Bean Validation `@Min(0) @Max(150)`                  |
| `XxxArgs.model_validate(dict)` | Jackson 反序列化 + `Validator.validate()`            |
| `model_json_schema()`          | OpenAPI / Swagger schema（springdoc 自动生成的那个） |
| `ValidationError.errors()`     | `ConstraintViolation` 列表                           |
| `model_dump()`                 | Jackson 序列化成 Map/JSON                            |

**一句话：Pydantic = DTO + Bean Validation + Jackson，三合一。**

你写 Java 时：

java

```
public class DeletePersonArgs {
    @NotBlank private String name;
    @Min(0) @Max(150) private int age;
}
```



Python 里就是：

python

```
class DeletePersonArgs(BaseModel):
    name: str
    age: int = Field(ge=0, le=150)
```

## Schema是干什么的

> **Schema 描述的是"一个数据长什么样"——有哪些字段、每个字段什么类型、有什么约束。**

函数参数只是一种"数据"。同一个 schema 机制，既能描述函数参数，也能描述 HTTP 请求体、数据库行、消息队列消息……

在 LLM 场景里，它描述的是：**LLM 该返回一个什么形状的 JSON。**这个 JSON 是给 LLM 看的——因为 LLM 的 API 只认 JSON 格式的工具定义（OpenAI / Anthropic 的 function calling 都要求 JSON）。

用 Java 的话说，`model_json_schema()` 生成的就是**这个东西的 OpenAPI 定义**：

json

```
{
  "properties": {
    "name": {"type": "string"},
    "age":  {"type": "integer", "minimum": 0, "maximum": 150}
  },
  "required": ["name", "age"]
}
```



你在 Java 里写过 Swagger 注解、看过 `/v3/api-docs`，那个 JSON 就是 schema。**它描述的是"一个对象的结构"，不是"一个函数"。**

## 为什么 LLM 场景需要 Pydantic？

这是 Java 里没有的新问题。Java 的 DTO 是**程序员之间**的契约——你写 `DeletePersonArgs`，我写调用方，编译期就对齐了。

但 LLM 是**外部不可信的黑盒**，它返回的是**运行时才生成的 JSON 字符串**：

python

```
# LLM 可能返回这些鬼东西：
{"name": "张三", "age": 30}          # 正常
{"name": "张三"}                      # 少字段
{"name": "张三", "age": "三十"}       # 类型错
{"name": "张三", "age": -5}           # 违反约束
{"user_name": "张三", "age": 30}      # key 名错了
```

**没有编译期检查，没有类型保证。** 你需要一个东西：

1. 把"参数该长什么样"**告诉** LLM（→ `model_json_schema()` 塞进 prompt / tool 定义）
2. 把 LLM 返回的 JSON **校验**成可信对象（→ `model_validate()`）
3. 校验失败时给出**结构化错误**回传 LLM 重试（→ `ValidationError.errors()`）

Pydantic 就是干这三件事的。

# Day2-2026-9-23日（实现tool幂等）

## tool_execution_repository是干嘛的？

它自己不调用 Tool，也不操作数据库。它负责回答两个问题：

1. 当前 Tool 是否依赖前面的某个 Tool？

2. 如何把前一个 Tool 的执行结果，填入后一个 Tool 的参数？

   ## 为什么需要它

   假设用户说：

   > 帮我查询张三的详细信息。

   大模型不能直接调用：

   ```
   get_person_detail(person_id="???")
   ```

   因为用户提供的是“张三”，而 `get_person_detail` 需要数据库中的 `person_id`。

   因此必须分两步：

   ```
   第一步：find_person(query="张三")
                    ↓
           得到 person_id="p_123"
                    ↓
   第二步：get_person_detail(person_id="p_123")
   ```

   问题在于：任务规划阶段还没有执行 `find_person`，所以大模型不知道 `p_123`。

   `tool_dependencies.py` 就是用来表达和解决这种“前一步结果是后一步参数”的场景。

## 如何表示tool之间的依赖关系

第一步查找人物：

```
{
  "step_id": "find_target",
  "tool": "find_person",
  "args": {
    "query": "张三",
    "search_mode": "exact"
  }
}
```

第二步查询详情：

```
{
  "step_id": "get_target_detail",
  "tool": "get_person_detail",
  "depends_on": ["find_target"],
  "args": {
    "person_id": {
      "$ref": {
        "step_id": "find_target",
        "path": "data.id"
      }
    }
  }
}
```

这里有三个关键字段。

### `step_id`

```
"step_id": "find_target"
```

表示任务计划中的步骤名称。

它由大模型生成，主要用于表达依赖关系：

```
find_target
get_target_detail
delete_target
```

`step_id` 只在当前任务计划内有效。

### `depends_on`

```
"depends_on": ["find_target"]
```

表示当前步骤必须等 `find_target` 成功后才能执行。

如果 `find_target` 失败：

```
find_target = FAILED
```

那么后面的任务会被标记为：

```
get_target_detail = SKIPPED
```

## 如果一个thread_id有多个中断，用户resume，如何确定resume哪一个？

你实现的 `call_id` 保持不变：

- `thread_id`：定位会话。
- `interrupt_id`：定位具体暂停点。
- `call_id`：定位具体 Tool 调用，用于审计和幂等。

已验证真实链路：LangGraph 自动生成中断 ID、检查点能找到该 ID、按 ID 恢复后才注入删除授权。现有 10 项检查全部通过，没有新增测试文件。官方的多中断恢复也是采用 ID 到恢复值的映射方式。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#handling-multiple-interrupts)

## （重点）请求级别的幂等（request_id）：

```
提问：我举个例子，下单流程，有一个订单库，用户使用agent下单，需要新增订单tool
新增订单生成call_id为：a1
假设，新增订单工具执行成功，生成了订单号，但还未返回成功，此时系统崩溃。前端未收到成功消息，超时后，给用户显示“重试”的按钮，用户点击重试，前端怎么才能拿到a1呢？怎么获取到a1然后查询数据库这一次tool有没有执行成功
```

企业级做法是：**前端先生成并持有一个稳定的请求幂等键，后端再把它和 `call_id` 建立映射。**

### 三种 ID 的职责

| ID           | 生成方       | 作用                             |
| ------------ | ------------ | -------------------------------- |
| `thread_id`  | 前端或后端   | 标识一段 Agent 会话              |
| `request_id` | 前端         | 标识用户这一次“下单”请求         |
| `call_id`    | Agent 执行器 | 标识这次工作流中的具体 Tool 调用 |
| `order_no`   | 订单系统     | 标识最终业务订单                 |

`thread_id` 不能代替 `request_id`，因为同一个会话里可以下多次订单。

### 完整执行流程

前端在用户第一次点击“下单”时生成：

```
thread_id  = t100
request_id = r100
```

在调用订单 Tool 之前，保存映射：

```
request_id: r100
thread_id:  t100
call_id:    a1
status:     running
```

订单 Tool 使用稳定的业务幂等键创建订单：

```
create_order(
    product_id="phone-001",
    quantity=1,
    idempotency_key="r100:a1",
)
```

订单库保存：

```
order_no:       O202609230001
idempotency_key: r100:a1
```

**恢复时必须从 checkpoint 读取原来的 `tool_calls`，直接继续执行 `a1`，不要重新让模型规划一次。重新规划可能生成新的 `call_id=a2`，这会把同一次业务请求变成另一项任务。**

所以这里的关键关系是：

```
前端重试
   ↓ 携带原 request_id
找到原 Agent 请求
   ↓
找到原 LangGraph thread/checkpoint
   ↓
恢复原 call_id
   ↓
使用业务幂等键查询订单库
   ↓
返回原订单
```

你现在的 `tool_execution` 只记录 `thread_id + call_id` 还不够。下一步应该增加一层 **Agent 请求表**，至少记录：

```
request_id
thread_id
status
result
error_message
created_at
updated_at
```

然后在 `tool_execution` 表中增加 `request_id`，形成：

```
request_id → call_id → order idempotency_key → order_no
```

这是你下一步最应该实现的部分。完成后，你的重试机制才能覆盖“业务已经成功，但 Agent 没来得及返回结果”的场景。

## （重点）为什么执行tool不直接使用MySQL的事务？

假设这样设计：

```
开启MySQL事务
    ↓
插入 running
    ↓
一直不提交，持有行锁
    ↓
调用Embedding API
    ↓
写Neo4j
    ↓
写Chroma
    ↓
更新success
    ↓
提交事务
```

虽然其他线程会等待，但会带来几个问题。

### 1. Tool可能执行很久

一次 Agent Tool 可能需要几秒甚至几十秒。

这段时间 MySQL 一直占用：

- 数据库连接；
- 行锁；
- 未提交事务；
- undo log；
- 连接池资源。

并发量上来后，很容易出现：

```
连接池耗尽
锁等待超时
死锁概率增加
HTTP请求大量堆积
```

数据库事务应该尽可能短，不适合覆盖模型调用或跨数据库调用。

### 2. 进程崩溃仍然无法解决重复副作用

假设执行过程是：

```
MySQL事务未提交
    ↓
Neo4j创建人物成功
    ↓
进程崩溃
```

进程崩溃后，MySQL 会自动回滚：

```
tool_execution记录消失
```

但 Neo4j 不会跟着回滚：

```
Person已经存在
```

另一个线程获得锁以后，会认为这次 Tool 从未执行，再创建一次人物。

所以，长事务仍然无法解决跨数据库一致性。

### 3. 等待行锁不一定适合HTTP请求

假设第一个 Tool 要执行30秒，后面十个重复请求都在等待锁：

```
请求1：执行Tool
请求2：等待数据库锁
请求3：等待数据库锁
请求4：等待数据库锁
...
```

这些请求会一直占用 Web 服务线程、协程、数据库连接。

更常见的企业级处理方式是：

```
第一次请求 → 获得执行权，开始执行
重复请求   → 立即返回 IN_PROGRESS
前端       → 稍后查询状态
```

例如返回：

```
{
  "request_id": "r100",
  "status": "RUNNING",
  "message": "任务正在处理中"
}
```

而不是让每个请求都阻塞等待。

### 4.当前方案其实也使用了数据库事务

你现在的实现并不是完全放弃事务，而是采用**短事务抢占**：

```
开启事务
    ↓
尝试INSERT running
    ↓
立即提交
    ↓
释放数据库连接和锁
    ↓
执行耗时Tool
```

完成后再使用一个短事务：

```
开启事务
    ↓
UPDATE success
    WHERE execution_token = 当前token
    ↓
提交
```

它的设计目标是：

- 用数据库唯一键决定谁获得执行权；
- 不长时间持有数据库连接；
- 重复请求快速得到 `IN_PROGRESS`；
- 旧进程不能覆盖新进程的结果。

`execution_token` 本质上是一种**执行权凭证**：

```
call_id告诉我们：这是哪个任务
execution_token告诉我们：现在由哪个执行者负责
```

### 5.两种方式应该组合使用

推荐方案不是只使用事务或者只使用 `execution_token`，而是分层使用：

| 场景                    | 推荐方案                      |
| ----------------------- | ----------------------------- |
| 抢占Tool执行权          | MySQL短事务、唯一键、条件更新 |
| 防止旧进程更新状态      | `execution_token`             |
| 同一个MySQL里的业务写入 | 同一个数据库事务              |
| Neo4j业务写入           | 业务幂等键和唯一约束          |
| Chroma索引写入          | 可重试的异步索引任务          |
| 重复HTTP请求            | 返回`IN_PROGRESS`，由前端查询 |

## （面试话术）tool执行涉及到分布式事务相关

更成熟的表达是：**先划分一致性等级，再根据业务边界选择方案。**

```
我的项目一次 Agent Tool 调用可能同时涉及 MySQL、Neo4j 和 ChromaDB，因此存在分布式一致性问题。

我没有让 MySQL 长事务覆盖整个 Tool 执行过程，因为 Tool 还会调用 Neo4j、向量数据库和外部模型服务。这样会长期占用数据库连接和行锁，容易造成锁等待、连接池耗尽，也不能真正回滚其他数据库已经产生的副作用。

我的设计是先通过 MySQL 短事务和唯一键抢占 Tool 执行权。没有抢到执行权的请求立即返回“正在执行”，由前端稍后查询状态，不阻塞数据库连接。

执行过程中使用 call_id 标识任务，使用 execution_token 标识当前执行者，防止超时后旧进程恢复并覆盖新进程的执行结果。对于 Neo4j 写操作，还需要把 call_id 作为业务幂等键，保证 Tool 重试时返回原来的业务结果。ChromaDB 只作为可重建的搜索索引，采用异步更新、失败重试和最终一致性。

如果业务对一致性要求更高，我会先尝试缩小事务边界，把核心数据放在同一个事务数据库中。例如金融账务的核心记账应该尽量在同一个数据库本地事务中完成，其他通知、搜索索引和统计通过事件异步更新。

如果确实无法避免跨服务事务，再根据业务场景选择方案：

- 对少量、可控的数据库资源，并且确实要求强一致时，可以评估 XA 或 2PC，但需要接受阻塞、性能和可用性方面的代价。
- 对库存冻结、余额预留等具有明确确认和撤销动作的业务，可以使用 TCC。
- 对持续时间较长、每一步都能定义补偿操作的业务流程，可以使用 Saga。
- 对订单创建后发送通知、更新索引等场景，可以使用本地事务加 Outbox、消息队列、消费者幂等和补偿重试，实现最终一致性。
- 对金融类业务，除了事务方案，还需要唯一业务流水号、不可变审计记录、对账和差错补偿机制。

因此我不会简单地认为一致性要求高就一定要上分布式事务，而是先区分哪些数据必须强一致，哪些数据允许最终一致，再选择成本合适的方案。
```

| 方案         | 一致性           | 适合场景               |
| ------------ | ---------------- | ---------------------- |
| 单库本地事务 | 强一致           | 订单与核心账务         |

## 观察节点设计：执行与决策分离

### 一、问题：传统做法存在的问题

大多数 LangGraph demo 里，`execute_tools` 节点长这样：

```python
# ❌ 传统写法：执行和决策混在一起
def execute_tools(state):
    results = []
    for call in state["tool_calls"]:
        result = execute_tool(call["tool"], **call["args"])
        results.append(result)
    state["tool_results"] = results

    # 直接在同一个函数里判断下一步
    if all(r["success"] for r in results):
        return Command(goto="generate_response")
    elif "已存在" in results[0].get("msg", ""):
        return Command(goto="ask_clarification")
    else:
         # ... 更多字符串判断
```

三个致命问题：

1. **决策依赖文案匹配** — `"已存在" in msg` 这种判断，Tool 维护者改一下措辞，路由就崩了
2. **不可审计** — 同样的执行结果，模型生成的路由每次可能不一样，出问题找不到原因
3. **重试逻辑散落** — 什么时候能自动重规划、什么时候必须问用户，散在各个 if-else 里

### 二、解决方案：执行事实 → 观察决策，两段式管道

新的 execute_tools **只记录事实**，决策完全交给 observe_execution：

复制

```
execute_tools                    observe_execution
  ┌──────────────┐                ┌─────────────────────┐
  │  执行 Tool    │                │  读 tool_results    │
  │  记录结果     │ ─── state ──→  │  读 error_codes     │
  │  打 error_code│                │  纯 Python 策略     │
  │  不判断路由   │                │  输出 4 种决策      │
  └──────────────┘                └─────────────────────┘
```

#### 2.1 执行端：只生产结构化事实

`execute_tools` 里每个步骤收尾只有一件事——打结构化记录：

```python
# execute_tools.py — _record 函数
def _record(call, status, *, result=None, error=None, error_code=None):
    return {
        "step_id": call["step_id"],      # 规划阶段分配的步骤 ID
        "call_id": call["call_id"],      # 幂等键
        "tool": call["tool"],
        "status": status.value,          # SUCCESS / FAILED / SKIPPED（枚举，非字符串匹配）
        "result": result,                # Tool 原始返回，含 data
        "error": error,                  # 人类可读错误（仅用于展示，不做判断）
        "error_code": error_code.value if error_code else None,  # 机器可读（用于路由）
    }
```

**同一个 Tool 调用，不管成功还是失败，记录格式完全一样。** 观察节点不需要解析异常信息。

失败时补打 `error_code`，来自 Tool 返回的结构化协议：

```python
# Tool 失败时应该返回这种格式
# {"success": False, "error_code": "NOT_FOUND", "message": "未找到张三", "data": {}}

def _append_problem(records, errors, call, *, message, error_code, status=FAILED, result=None):
    records.append(_record(call, status, result=result, error=message, error_code=error_code))
    errors.append(message)
```

#### 2.2 观察端：确定性路由

`observe_execution` 的入口只有三行：

```python
# observe_execution.py
def observe_execution(state: AgentState) -> Command:
    observation = _observe(state)                      # ① 读事实，不调 LLM
    update = _observation_update(state, observation)    # ② 打包反馈数据
    return _route_decision(state, observation, update)  # ③ 映射为 Command 路由
```

### 四、分离带来了什么

| 维度       | 传统做法                     | 本设计                                      |
| ---------- | ---------------------------- | ------------------------------------------- |
| 错误判断   | 字符串匹配 `"已存在" in msg` | 结构化 `error_code` 枚举                    |
| 路由决策   | 执行节点里 if-else 散落      | 集中到 `observe_tool_results`，纯 Python    |
| 可审计性   | 每次路由可能不同             | 确定性函数，给定同样输入必输出同样决策      |
| 重规划安全 | 容易重复写操作               | 检查 `successful_mutations`，有副作用就禁止 |
| 测试       | 需要 mock LLM                | `observe_tool_results` 可以直接单元测试     |

这个设计的核心思想一句话：**LLM 负责理解"用户想做什么"和"该怎么回应"，确定性代码负责判断"当前能不能安全地继续"以及"下一步应该走哪条路"。** 两个领域有完全不同的可靠性要求，不应该让 LLM 同时承担。



## 多个独立错误如何处理

如果 A、B、C 是彼此独立的步骤，可能同时出现多个真实错误。这时需要设置决策优先级。

推荐顺序：

```
PERMISSION_DENIED / INTERNAL
    ↓
AMBIGUOUS / CONFLICT
    ↓
IN_PROGRESS / TRANSIENT
    ↓
NOT_FOUND / INVALID_ARGUMENT
    ↓
DEPENDENCY_FAILED
```

例如同时出现：

```
B = PERMISSION_DENIED
E = NOT_FOUND
```

**必须先停止处理权限问题，不能因为 `E` 可以重规划，就忽略 `B` 的越权风险。**

## 已经产生写副作用如何处理

```
A 查询人物成功
B 新增人物成功
C 新增关系失败
```

这时不能简单把整个计划重新执行，因为 B 已经产生了写副作用。

当前策略是：

```
只要已有写 Tool 成功，就禁止自动重新规划
```

```
我的项目采用 Plan、Act、Observe、Decide 的闭环架构。
```

## 1、五个 ID 分别解决什么问题

| ID                | 生命周期             | 谁生成               | 解决的问题                                      |
| ----------------- | -------------------- | -------------------- | ----------------------------------------------- |
| `conversation_id` | 一段连续会话         | 服务端创建并校验归属 | 这些消息属于哪一个聊天窗口                      |
| `message_id`      | 一条具体消息用户消息 | 服务端生成UUID       | 一条具体消息用户消息、Agent 回复分别有自己的 ID |
| `request_id`      | 用户的一次提问       | 前端生成 UUID        | HTTP 重试和业务幂等                             |
| `thread_id`       | LangGraph 运行线程   | 服务端生成           | 去哪个 Checkpoint 恢复 Agent                    |
| `interrupt_id`    | 一次暂停点           | LangGraph 生成       | 恢复具体哪一次确认或澄清                        |

### 1.1、conversation_id生成方式：

用户A
├── conv_001：维护客户张三
├── conv_002：维护客户李四
└── conv_003：查询家庭关系

conversation_id到后期可以用于区分，不同的客户聊天，目前暂时使用“default”。

```python
DEFAULT_CONVERSATION_ID = "default"
```

### 1.2、thread_id生成方式：

**thread_id和conversation_id可以保持一对一的关系（现在thread_id生成方式已经是一对一关系了），但是最好是分开**：假设以后升级 Agent 状态结构，需要抛弃旧 Checkpoint：

- 一个会话需要重新运行 Agent，产生新的 `thread_id`。
- 删除 Checkpoint，但保留聊天记录用于审计。
- 从企业微信导入聊天消息，这些消息有 `conversation_id`，但还没有 LangGraph `thread_id`。
- 同一个业务会话可能产生主流程、后台摘要流程等多个执行线程。

```python
def derive_thread_id(owner_id: str) -> str:

    第一版每个用户只有一个 Agent 会话，足够跑通学习链路。
    TODO(你来实现)：支持多会话时，把服务端校验过的 conversation_id 加入原文，

    raw = f"relationship-agent:v1:{owner_id}:{DEFAULT_CONVERSATION_ID}"
```

## 2、三层职责

不要把“最近消息、摘要、长期事实”简单理解成三张表。本项目的分层是：

| 层次                 | 保存内容                                 | 解决的问题               | 存储位置                 |
| -------------------- | ---------------------------------------- | ------------------------ | ------------------------ |
| 第一层：执行状态记忆 | 当前节点、Tool 计划、interrupt、执行结果 | 服务重启后如何继续执行   | LangGraph Checkpointer   |
| 第二层：会话记忆     | 最近消息、原始消息、滚动摘要             | 用户之前聊过什么         | PostgreSQL               |
| 第三层：长期业务记忆 | 人物资料、关系事实、证据、版本           | 哪些客户信息可以长期使用 | PostgreSQL `memory_fact` |

### 2.1 第一层：运行状态记忆

由 LangGraph PostgreSQL Checkpointer 管理：

- 当前节点和下一跳；
- `interrupt_id` 与待确认内容；
- 当前 Tool 计划、执行结果、重规划反馈；
- 当前会话的紧凑状态、摘要游标和上下文统计。

Checkpointer 不是聊天记录查询库，也不是长期客户画像。前端历史记录和审计查询不
直接读取 LangGraph 内部表。

### 2.2 第二层：短期对话记忆

PostgreSQL 业务表保存原始用户/助手消息，AgentState 只保留运行需要的紧凑副本：

- 最近若干轮原始消息；
- 一份滚动结构化摘要；
- 摘要覆盖到的最后一个 `message_id`；
- 本轮构造上下文时的 Token 统计。

滚动摘要必须保留：已确认人物、已确认关系、用户目标、重要决定、待解决问题和
未完成任务。摘要不能把模型推断升级为已确认事实。

### 2.3 第三层：长期业务记忆

长期记忆以“事实”而不是整段聊天保存：

- `owner_id`：租户隔离；
- `person_id`：事实所属人物；
- `category` 与结构化 `value`；
- `status`、`version`、`valid_from`、`valid_to`；
- `confidence`；
- 来源消息 `message_id`；
- 是否需要用户确认；
- 被哪条新事实替代。

模型只产生候选事实。确定性代码校验证据、owner 和版本后才能写入。矛盾、敏感或
低置信度事实进入待确认状态，不能直接污染客户画像。

### 2.5、摘要为什么必须结构化

> 用户：确认了，他是我同事。但我还没确定他属于哪个部门。

- `confirmed_people`、`confirmed_relations`：目前明确确认的人物和关系。
- `uncertainties`：仍有疑问的内容，不能当作确定事实使用。
- `open_questions`：还需要向用户确认的问题，例如“张三属于哪个部门？”

### 3.4、 为什么排除 note

```

gender

occupation
education
hobbies
personality

```

`note` 不会自动变成 active 长期事实。

### 3.5、Repository 还要再次检查什么

即使候选来自成功 Tool，也不能直接 INSERT。

```
owner_id 是否存在
```

> 模型和上游节点只能提出候选，数据仓储才拥有最终写入权限。

## **1、如何实现代词指代解析（Anaphora Resolution）**。

### 1.1、 正则表达式

```python
_LEADING_REFERENCE = re.compile(
    r"^\s*(?:那)?(?:他|她|这个人|那个人|这位|那位)(?:的|是|有|和|与|怎么|什么|呢|吗|[？?\s]|$)"
)
```

- **作用**：它用来判断用户的输入是不是以“单数第三人称代词”开头的追问（比如“他呢”、“她喜欢什么”、“那个人是谁”）。
- **设计亮点**：
  - `^\s*(?:那)?`：允许开头有空格，并允许“那”作为语气词（如“那他是谁”）。
  - 紧跟着必须是明确的单数代词（他/她/这个人等）。
  - 后面必须紧跟特定的助词、动词或标点（如“的”、“是”、“有”、“怎么”、“什么”等），或者直接结束/跟标点。这保证了“他”确实是一个作为主语的指代，避免了“他乡遇故知”这种“他”作为构词成分的误判。



### 2.2、提取焦点人物（`derive_focus` 函数）

- **作用**：从**本轮**已经成功执行过的工具调用结果（`tool_results`）中，提取出“焦点人物”。
- **工作流程**：
  - 遍历工具结果，只筛选出与人物相关的工具（`_PERSON_TOOLS`，如查找人物、获取详情等）。
  - 要求状态必须是 `SUCCESS`，且返回的数据中包含有效的 `person_id` 和 `name`。
  - 利用字典 `people` 以 `person_id` 为键进行去重。
- **返回逻辑**：
  - 如果刚好只有 **1** 个成功的人物结果，它会将这个人物作为“焦点”（附带 owner_id、conversation_id 等上下文），返回焦点对象。
  - 如果有 **0 个或多个**，则视为无法确立唯一焦点，返回 `None` 和 `candidates`（候选人列表）。



### 3. 解决指代（`resolve_reference` 函数）

```python
def resolve_reference(state: dict[str, Any]) -> dict[str, Any]:
```

- **作用**：核心决策引擎。根据用户输入和当前状态，决定如何处理代词。
- **返回的三种状态**：
  - **`SKIP`（跳过）**：用户的输入不是指代句（校验不通过），或者输入包含“用户补充：”（可能是系统自动补全的内容，防污染）。直接跳过，交给常规逻辑处理。
  - **`RESOLVED`（已解决）**：状态中存在有效的 `person_focus`，并且它的 `owner_id` 和 `conversation_id` 与当前会话完全一致。系统直接把代词映射为这个焦点人物，继续执行。
  - **`CLARIFY`（要求澄清）**：如果 `person_focus` 没有命中（比如跨会话了，或者上一轮也没确定唯一人物），它会去检查 `person_focus_candidates`（候选列表）。同样，它**强制校验**候选列表必须属于当前的 `owner_id` 和 `conversation_id`。如果符合，最多取前 5 个候选人返回，让上层逻辑向用户反问：“您指的是张三还是李四？”
- **安全边界**：代码多次强调 `owner_id` 和 `conversation_id` 的匹配（`focus.get("owner_id") == owner_id`），这是非常关键的安全设计，防止 A 用户看到 B 用户的人物焦点，也防止跨对话串台。
