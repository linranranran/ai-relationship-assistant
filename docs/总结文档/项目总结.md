

# Day1-2026-9-22日

## sanitize_model_tool_calls函数是干嘛的？

`sanitize_model_tool_calls()` 是大模型输出和真实 Tool 执行之间的一道“安全检查门”。

大模型生成的 Tool 调用不能直接执行。这个函数负责把模型输出的计划检查、清洗并转换成系统能够信任的调用计划。

例如，大模型可能输出：

```
[
    {
        "tool": "delete_person",
        "args": {
            "person_id": "p_123",
            "owner_id": "别人的用户ID",
            "confirmed": True
        }
    }
]
```

如果直接执行，就会出现两个严重问题：

- 模型可以指定其他用户的 `owner_id`，造成越权访问。
- 模型可以自己生成 `confirmed=True`，绕过人工确认。

所以这个函数会把危险参数删除，得到：

```
[
    {
        "tool": "delete_person",
        "args": {
            "person_id": "p_123"
        }
    }
]
```

后面系统会：

1. 从登录令牌中注入可信的 `owner_id`。
2. 进入 `request_confirmation` 节点。
3. 用户明确确认后，由服务端注入 `confirmed=True`。
4. 最后才执行 `delete_person`。

## 它处在什么位置

完整链路是：

```
用户输入
   ↓
大模型规划 Tool
   ↓
sanitize_model_tool_calls
   ↓
风险判断
   ├─ 普通操作 → execute_tools
   └─ 删除操作 → interrupt → 用户确认 → execute_tools
```

大模型的输出属于“不可信输入”，性质上和前端参数相似。即使 Prompt 明确告诉模型不要输出某些字段，也不能保证模型永远遵守。

## 它干了什么

1. 确认最外层是列表
2. 过滤格式错误的调用

3. 保证 `args` 是字典

4. 删除模型无权控制的字段

5. 校验 Tool 参数

6. 拒绝未知 Tool

7. 生成 `call_id`

   一次任务里可能存在多个 Tool 调用：

   ```
   [
       {
           "tool": "find_person",
           "args": {"query": "张三"}
       },
       {
           "tool": "delete_person",
           "args": {"person_id": "p_123"}
       }
   ]
   ```

   清洗后，可以为每个调用生成唯一 ID：

   ```
   {
       "call_id": "call_abc123",
       "tool": "delete_person",
       "args": {
           "person_id": "p_123"
       }
   }
   ```

   它主要解决重复执行问题。

   例如：

   ```
   1. 用户点击“确认删除”
   2. 后端成功删除张三
   3. 网络在返回响应时中断
   4. 前端认为请求失败，再次发送恢复请求
   5. 后端第二次执行删除
   ```

   有了 `call_id`，执行 Tool 前可以查询执行记录：

   ```
   record = find_execution_record(call_id)
   
   if record and record.status == "SUCCESS":
       return record.result
   ```

   这样同一个调用即使收到两次，也只真正执行一次。

   它还可以用于审计：

   ```
   operation_id: op_001
   call_id: call_002
   owner_id: user_123
   tool: delete_person
   status: SUCCESS
   confirmed_by_user: true
   executed_at: 2026-09-22 15:20:00
   ```

   其中：

   - `operation_id` 表示一整次用户操作。
   - `call_id` 表示这次操作中的某一个 Tool 调用。

   例如：

   ```
   operation_id = 删除张三这项任务
   
   call_1 = 查询张三
   call_2 = 查询张三关联关系
   call_3 = 删除张三
   call_4 = 删除张三的向量数据
   ```

## 它解决的核心场景

这个函数主要解决四类问题：

1. **模型输出不稳定**

   模型可能缺少字段、给错类型或者输出不存在的 Tool。

2. **权限越界**

   模型可能生成其他用户的 `owner_id`，因此身份字段必须由服务端注入。

3. **绕过人工确认**

   模型可能根据用户对话自行推测“用户已经同意”，但只有 `/resume` 接口才能代表结构化确认。

4. **重复执行**

   网络重试、服务恢复或前端重复点击都可能让写操作执行两次，所以每个调用需要稳定的 `call_id`。

你可以把这个函数理解为：

```
大模型生成的是“执行建议”
sanitize_model_tool_calls 输出的是“通过系统检查的执行计划”
```

它不是普通的数据格式化函数，而是 Agent 从“能调用工具”走向“可靠调用工具”的关键边界。

## Pydantic是干什么的

你在 Java 里其实天天用这套东西，只是叫法不同：

| Python / Pydantic              | Java 对应物                                          |
| :----------------------------- | :--------------------------------------------------- |
| `class XxxArgs(BaseModel)`     | DTO / POJO                                           |
| 字段类型注解 `name: str`       | `private String name;`                               |
| `Field(ge=0, le=150)`          | Bean Validation `@Min(0) @Max(150)`                  |
| `XxxArgs.model_validate(dict)` | Jackson 反序列化 + `Validator.validate()`            |
| `model_json_schema()`          | OpenAPI / Swagger schema（springdoc 自动生成的那个） |
| `ValidationError.errors()`     | `ConstraintViolation` 列表                           |
| `model_dump()`                 | Jackson 序列化成 Map/JSON                            |

**一句话：Pydantic = DTO + Bean Validation + Jackson，三合一。**

你写 Java 时：

java

```
public class DeletePersonArgs {
    @NotBlank private String name;
    @Min(0) @Max(150) private int age;
}
```



Python 里就是：

python

```
class DeletePersonArgs(BaseModel):
    name: str
    age: int = Field(ge=0, le=150)
```

## Schema是干什么的

> **Schema 描述的是"一个数据长什么样"——有哪些字段、每个字段什么类型、有什么约束。**

函数参数只是一种"数据"。同一个 schema 机制，既能描述函数参数，也能描述 HTTP 请求体、数据库行、消息队列消息……

在 LLM 场景里，它描述的是：**LLM 该返回一个什么形状的 JSON。**这个 JSON 是给 LLM 看的——因为 LLM 的 API 只认 JSON 格式的工具定义（OpenAI / Anthropic 的 function calling 都要求 JSON）。

用 Java 的话说，`model_json_schema()` 生成的就是**这个东西的 OpenAPI 定义**：

json

```
{
  "properties": {
    "name": {"type": "string"},
    "age":  {"type": "integer", "minimum": 0, "maximum": 150}
  },
  "required": ["name", "age"]
}
```



你在 Java 里写过 Swagger 注解、看过 `/v3/api-docs`，那个 JSON 就是 schema。**它描述的是"一个对象的结构"，不是"一个函数"。**

## 为什么 LLM 场景需要 Pydantic？

这是 Java 里没有的新问题。Java 的 DTO 是**程序员之间**的契约——你写 `DeletePersonArgs`，我写调用方，编译期就对齐了。

但 LLM 是**外部不可信的黑盒**，它返回的是**运行时才生成的 JSON 字符串**：

python

```
# LLM 可能返回这些鬼东西：
{"name": "张三", "age": 30}          # 正常
{"name": "张三"}                      # 少字段
{"name": "张三", "age": "三十"}       # 类型错
{"name": "张三", "age": -5}           # 违反约束
{"user_name": "张三", "age": 30}      # key 名错了
```

**没有编译期检查，没有类型保证。** 你需要一个东西：

1. 把"参数该长什么样"**告诉** LLM（→ `model_json_schema()` 塞进 prompt / tool 定义）
2. 把 LLM 返回的 JSON **校验**成可信对象（→ `model_validate()`）
3. 校验失败时给出**结构化错误**回传 LLM 重试（→ `ValidationError.errors()`）

Pydantic 就是干这三件事的。

# Day2-2026-9-23日（实现tool幂等）

## 1、tool_execution_repository是干嘛的？

它自己不调用 Tool，也不操作数据库。它负责回答两个问题：

1. 当前 Tool 是否依赖前面的某个 Tool？

2. 如何把前一个 Tool 的执行结果，填入后一个 Tool 的参数？

   ## 为什么需要它

   假设用户说：

   > 帮我查询张三的详细信息。

   大模型不能直接调用：

   ```
   get_person_detail(person_id="???")
   ```

   因为用户提供的是“张三”，而 `get_person_detail` 需要数据库中的 `person_id`。

   因此必须分两步：

   ```
   第一步：find_person(query="张三")
                    ↓
           得到 person_id="p_123"
                    ↓
   第二步：get_person_detail(person_id="p_123")
   ```

   问题在于：任务规划阶段还没有执行 `find_person`，所以大模型不知道 `p_123`。

   `tool_dependencies.py` 就是用来表达和解决这种“前一步结果是后一步参数”的场景。

## 2、如何表示tool之间的依赖关系

第一步查找人物：

```
{
  "step_id": "find_target",
  "tool": "find_person",
  "args": {
    "query": "张三",
    "search_mode": "exact"
  }
}
```

第二步查询详情：

```
{
  "step_id": "get_target_detail",
  "tool": "get_person_detail",
  "depends_on": ["find_target"],
  "args": {
    "person_id": {
      "$ref": {
        "step_id": "find_target",
        "path": "data.id"
      }
    }
  }
}
```

这里有三个关键字段。

### `step_id`

```
"step_id": "find_target"
```

表示任务计划中的步骤名称。

它由大模型生成，主要用于表达依赖关系：

```
find_target
get_target_detail
delete_target
```

`step_id` 只在当前任务计划内有效。

### `depends_on`

```
"depends_on": ["find_target"]
```

表示当前步骤必须等 `find_target` 成功后才能执行。

如果 `find_target` 失败：

```
find_target = FAILED
```

那么后面的任务会被标记为：

```
get_target_detail = SKIPPED
```

## 3、如果一个thread_id有多个中断，用户resume，如何确定resume哪一个？

你实现的 `call_id` 保持不变：

- `thread_id`：定位会话。
- `interrupt_id`：定位具体暂停点。
- `call_id`：定位具体 Tool 调用，用于审计和幂等。

已验证真实链路：LangGraph 自动生成中断 ID、检查点能找到该 ID、按 ID 恢复后才注入删除授权。现有 10 项检查全部通过，没有新增测试文件。官方的多中断恢复也是采用 ID 到恢复值的映射方式。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#handling-multiple-interrupts)

## 4、（重点）请求级别的幂等（request_id）：

```
提问：我举个例子，下单流程，有一个订单库，用户使用agent下单，需要新增订单tool
新增订单生成call_id为：a1
假设，新增订单工具执行成功，生成了订单号，但还未返回成功，此时系统崩溃。前端未收到成功消息，超时后，给用户显示“重试”的按钮，用户点击重试，前端怎么才能拿到a1呢？怎么获取到a1然后查询数据库这一次tool有没有执行成功
```

企业级做法是：**前端先生成并持有一个稳定的请求幂等键，后端再把它和 `call_id` 建立映射。**

### 三种 ID 的职责

| ID           | 生成方       | 作用                             |
| ------------ | ------------ | -------------------------------- |
| `thread_id`  | 前端或后端   | 标识一段 Agent 会话              |
| `request_id` | 前端         | 标识用户这一次“下单”请求         |
| `call_id`    | Agent 执行器 | 标识这次工作流中的具体 Tool 调用 |
| `order_no`   | 订单系统     | 标识最终业务订单                 |

`thread_id` 不能代替 `request_id`，因为同一个会话里可以下多次订单。

### 完整执行流程

前端在用户第一次点击“下单”时生成：

```
thread_id  = t100
request_id = r100
```

在调用订单 Tool 之前，保存映射：

```
request_id: r100
thread_id:  t100
call_id:    a1
status:     running
```

订单 Tool 使用稳定的业务幂等键创建订单：

```
create_order(
    product_id="phone-001",
    quantity=1,
    idempotency_key="r100:a1",
)
```

订单库保存：

```
order_no:       O202609230001
idempotency_key: r100:a1
```

**恢复时必须从 checkpoint 读取原来的 `tool_calls`，直接继续执行 `a1`，不要重新让模型规划一次。重新规划可能生成新的 `call_id=a2`，这会把同一次业务请求变成另一项任务。**

所以这里的关键关系是：

```
前端重试
   ↓ 携带原 request_id
找到原 Agent 请求
   ↓
找到原 LangGraph thread/checkpoint
   ↓
恢复原 call_id
   ↓
使用业务幂等键查询订单库
   ↓
返回原订单
```

你现在的 `tool_execution` 只记录 `thread_id + call_id` 还不够。下一步应该增加一层 **Agent 请求表**，至少记录：

```
request_id
thread_id
status
result
error_message
created_at
updated_at
```

然后在 `tool_execution` 表中增加 `request_id`，形成：

```
request_id → call_id → order idempotency_key → order_no
```

这是你下一步最应该实现的部分。完成后，你的重试机制才能覆盖“业务已经成功，但 Agent 没来得及返回结果”的场景。

## 5、（重点）为什么执行tool不直接使用MySQL的事务？

假设这样设计：

```
开启MySQL事务
    ↓
插入 running
    ↓
一直不提交，持有行锁
    ↓
调用Embedding API
    ↓
写Neo4j
    ↓
写Chroma
    ↓
更新success
    ↓
提交事务
```

虽然其他线程会等待，但会带来几个问题。

### 1. Tool可能执行很久

一次 Agent Tool 可能需要几秒甚至几十秒。

这段时间 MySQL 一直占用：

- 数据库连接；
- 行锁；
- 未提交事务；
- undo log；
- 连接池资源。

并发量上来后，很容易出现：

```
连接池耗尽
锁等待超时
死锁概率增加
HTTP请求大量堆积
```

数据库事务应该尽可能短，不适合覆盖模型调用或跨数据库调用。

### 2. 进程崩溃仍然无法解决重复副作用

假设执行过程是：

```
MySQL事务未提交
    ↓
Neo4j创建人物成功
    ↓
进程崩溃
```

进程崩溃后，MySQL 会自动回滚：

```
tool_execution记录消失
```

但 Neo4j 不会跟着回滚：

```
Person已经存在
```

另一个线程获得锁以后，会认为这次 Tool 从未执行，再创建一次人物。

所以，长事务仍然无法解决跨数据库一致性。

### 3. 等待行锁不一定适合HTTP请求

假设第一个 Tool 要执行30秒，后面十个重复请求都在等待锁：

```
请求1：执行Tool
请求2：等待数据库锁
请求3：等待数据库锁
请求4：等待数据库锁
...
```

这些请求会一直占用 Web 服务线程、协程、数据库连接。

更常见的企业级处理方式是：

```
第一次请求 → 获得执行权，开始执行
重复请求   → 立即返回 IN_PROGRESS
前端       → 稍后查询状态
```

例如返回：

```
{
  "request_id": "r100",
  "status": "RUNNING",
  "message": "任务正在处理中"
}
```

而不是让每个请求都阻塞等待。

### 4.当前方案其实也使用了数据库事务

你现在的实现并不是完全放弃事务，而是采用**短事务抢占**：

```
开启事务
    ↓
尝试INSERT running
    ↓
立即提交
    ↓
释放数据库连接和锁
    ↓
执行耗时Tool
```

完成后再使用一个短事务：

```
开启事务
    ↓
UPDATE success
    WHERE execution_token = 当前token
    ↓
提交
```

它的设计目标是：

- 用数据库唯一键决定谁获得执行权；
- 不长时间持有数据库连接；
- 重复请求快速得到 `IN_PROGRESS`；
- 旧进程不能覆盖新进程的结果。

`execution_token` 本质上是一种**执行权凭证**：

```
call_id告诉我们：这是哪个任务
execution_token告诉我们：现在由哪个执行者负责
```

### 5.两种方式应该组合使用

推荐方案不是只使用事务或者只使用 `execution_token`，而是分层使用：

| 场景                    | 推荐方案                      |
| ----------------------- | ----------------------------- |
| 抢占Tool执行权          | MySQL短事务、唯一键、条件更新 |
| 防止旧进程更新状态      | `execution_token`             |
| 同一个MySQL里的业务写入 | 同一个数据库事务              |
| Neo4j业务写入           | 业务幂等键和唯一约束          |
| Chroma索引写入          | 可重试的异步索引任务          |
| 重复HTTP请求            | 返回`IN_PROGRESS`，由前端查询 |

## 6、（面试话术）tool执行涉及到分布式事务相关

更成熟的表达是：**先划分一致性等级，再根据业务边界选择方案。**

```
我的项目一次 Agent Tool 调用可能同时涉及 MySQL、Neo4j 和 ChromaDB，因此存在分布式一致性问题。

我没有让 MySQL 长事务覆盖整个 Tool 执行过程，因为 Tool 还会调用 Neo4j、向量数据库和外部模型服务。这样会长期占用数据库连接和行锁，容易造成锁等待、连接池耗尽，也不能真正回滚其他数据库已经产生的副作用。

我的设计是先通过 MySQL 短事务和唯一键抢占 Tool 执行权。没有抢到执行权的请求立即返回“正在执行”，由前端稍后查询状态，不阻塞数据库连接。

执行过程中使用 call_id 标识任务，使用 execution_token 标识当前执行者，防止超时后旧进程恢复并覆盖新进程的执行结果。对于 Neo4j 写操作，还需要把 call_id 作为业务幂等键，保证 Tool 重试时返回原来的业务结果。ChromaDB 只作为可重建的搜索索引，采用异步更新、失败重试和最终一致性。

如果业务对一致性要求更高，我会先尝试缩小事务边界，把核心数据放在同一个事务数据库中。例如金融账务的核心记账应该尽量在同一个数据库本地事务中完成，其他通知、搜索索引和统计通过事件异步更新。

如果确实无法避免跨服务事务，再根据业务场景选择方案：

- 对少量、可控的数据库资源，并且确实要求强一致时，可以评估 XA 或 2PC，但需要接受阻塞、性能和可用性方面的代价。
- 对库存冻结、余额预留等具有明确确认和撤销动作的业务，可以使用 TCC。
- 对持续时间较长、每一步都能定义补偿操作的业务流程，可以使用 Saga。
- 对订单创建后发送通知、更新索引等场景，可以使用本地事务加 Outbox、消息队列、消费者幂等和补偿重试，实现最终一致性。
- 对金融类业务，除了事务方案，还需要唯一业务流水号、不可变审计记录、对账和差错补偿机制。

因此我不会简单地认为一致性要求高就一定要上分布式事务，而是先区分哪些数据必须强一致，哪些数据允许最终一致，再选择成本合适的方案。
```

| 方案         | 一致性           | 适合场景               |
| ------------ | ---------------- | ---------------------- |
| 单库本地事务 | 强一致           | 订单与核心账务         |

## 观察节点设计：执行与决策分离

### 一、问题：传统做法存在的问题

大多数 LangGraph demo 里，`execute_tools` 节点长这样：

```python
# ❌ 传统写法：执行和决策混在一起
def execute_tools(state):
    results = []
    for call in state["tool_calls"]:
        result = execute_tool(call["tool"], **call["args"])
        results.append(result)
    state["tool_results"] = results

    # 直接在同一个函数里判断下一步
    if all(r["success"] for r in results):
        return Command(goto="generate_response")
    elif "已存在" in results[0].get("msg", ""):
        return Command(goto="ask_clarification")
    else:
         # ... 更多字符串判断
```

三个致命问题：

1. **决策依赖文案匹配** — `"已存在" in msg` 这种判断，Tool 维护者改一下措辞，路由就崩了
2. **不可审计** — 同样的执行结果，模型生成的路由每次可能不一样，出问题找不到原因
3. **重试逻辑散落** — 什么时候能自动重规划、什么时候必须问用户，散在各个 if-else 里

### 二、解决方案：执行事实 → 观察决策，两段式管道

新的 execute_tools **只记录事实**，决策完全交给 observe_execution：

复制

```
execute_tools                    observe_execution
  ┌──────────────┐                ┌─────────────────────┐
  │  执行 Tool    │                │  读 tool_results    │
  │  记录结果     │ ─── state ──→  │  读 error_codes     │
  │  打 error_code│                │  纯 Python 策略     │
  │  不判断路由   │                │  输出 4 种决策      │
  └──────────────┘                └─────────────────────┘
```

#### 2.1 执行端：只生产结构化事实

`execute_tools` 里每个步骤收尾只有一件事——打结构化记录：

```python
# execute_tools.py — _record 函数
def _record(call, status, *, result=None, error=None, error_code=None):
    return {
        "step_id": call["step_id"],      # 规划阶段分配的步骤 ID
        "call_id": call["call_id"],      # 幂等键
        "tool": call["tool"],
        "status": status.value,          # SUCCESS / FAILED / SKIPPED（枚举，非字符串匹配）
        "result": result,                # Tool 原始返回，含 data
        "error": error,                  # 人类可读错误（仅用于展示，不做判断）
        "error_code": error_code.value if error_code else None,  # 机器可读（用于路由）
    }
```

**同一个 Tool 调用，不管成功还是失败，记录格式完全一样。** 观察节点不需要解析异常信息。

失败时补打 `error_code`，来自 Tool 返回的结构化协议：

```python
# Tool 失败时应该返回这种格式
# {"success": False, "error_code": "NOT_FOUND", "message": "未找到张三", "data": {}}

def _append_problem(records, errors, call, *, message, error_code, status=FAILED, result=None):
    records.append(_record(call, status, result=result, error=message, error_code=error_code))
    errors.append(message)
```

#### 2.2 观察端：确定性路由

`observe_execution` 的入口只有三行：

```python
# observe_execution.py
def observe_execution(state: AgentState) -> Command:
    observation = _observe(state)                      # ① 读事实，不调 LLM
    update = _observation_update(state, observation)    # ② 打包反馈数据
    return _route_decision(state, observation, update)  # ③ 映射为 Command 路由
```

### 四、分离带来了什么

| 维度       | 传统做法                     | 本设计                                      |
| ---------- | ---------------------------- | ------------------------------------------- |
| 错误判断   | 字符串匹配 `"已存在" in msg` | 结构化 `error_code` 枚举                    |
| 路由决策   | 执行节点里 if-else 散落      | 集中到 `observe_tool_results`，纯 Python    |
| 可审计性   | 每次路由可能不同             | 确定性函数，给定同样输入必输出同样决策      |
| 重规划安全 | 容易重复写操作               | 检查 `successful_mutations`，有副作用就禁止 |
| 测试       | 需要 mock LLM                | `observe_tool_results` 可以直接单元测试     |

这个设计的核心思想一句话：**LLM 负责理解"用户想做什么"和"该怎么回应"，确定性代码负责判断"当前能不能安全地继续"以及"下一步应该走哪条路"。** 两个领域有完全不同的可靠性要求，不应该让 LLM 同时承担。



## 多个独立错误如何处理

如果 A、B、C 是彼此独立的步骤，可能同时出现多个真实错误。这时需要设置决策优先级。

推荐顺序：

```
PERMISSION_DENIED / INTERNAL
    ↓
AMBIGUOUS / CONFLICT
    ↓
IN_PROGRESS / TRANSIENT
    ↓
NOT_FOUND / INVALID_ARGUMENT
    ↓
DEPENDENCY_FAILED
```

例如同时出现：

```
B = PERMISSION_DENIED
E = NOT_FOUND
```

**必须先停止处理权限问题，不能因为 `E` 可以重规划，就忽略 `B` 的越权风险。**

C 新增关系失败

这时不能简单把整个计划重新执行，因为 B 已经产生了写副作用。

```
我的项目采用 Plan、Act、Observe、Decide 的闭环架构。

## 1、五个 ID 分别解决什么问题

| ID                | 生命周期             | 谁生成               | 解决的问题                                      |
| ----------------- | -------------------- | -------------------- | ----------------------------------------------- |
| `conversation_id` | 一段连续会话         | 服务端创建并校验归属 | 这些消息属于哪一个聊天窗口                      |

### 1.1、conversation_id生成方式：

用户A
├── conv_001：维护客户张三
├── conv_002：维护客户李四
└── conv_003：查询家庭关系

### 1.2、thread_id生成方式：

**thread_id和conversation_id可以保持一对一的关系（现在thread_id生成方式已经是一对一关系了），但是最好是分开**：假设以后升级 Agent 状态结构，需要抛弃旧 Checkpoint：

- 删除 Checkpoint，但保留聊天记录用于审计。
- 从企业微信导入聊天消息，这些消息有 `conversation_id`，但还没有 LangGraph `thread_id`。

## 2、三层职责

不要把“最近消息、摘要、长期事实”简单理解成三张表。本项目的分层是：

| 层次                 | 保存内容                                 | 解决的问题               | 存储位置                 |
| -------------------- | ---------------------------------------- | ------------------------ | ------------------------ |
| 第一层：执行状态记忆 | 当前节点、Tool 计划、interrupt、执行结果 | 服务重启后如何继续执行   | LangGraph Checkpointer   |
| 第二层：会话记忆     | 最近消息、原始消息、滚动摘要             | 用户之前聊过什么         | PostgreSQL               |
| 第三层：长期业务记忆 | 人物资料、关系事实、证据、版本           | 哪些客户信息可以长期使用 | PostgreSQL `memory_fact` |

### 2.1 第一层：运行状态记忆

由 LangGraph PostgreSQL Checkpointer 管理：

- 当前节点和下一跳；
- `interrupt_id` 与待确认内容；
- 当前 Tool 计划、执行结果、重规划反馈；
- 当前会话的紧凑状态、摘要游标和上下文统计。

Checkpointer 不是聊天记录查询库，也不是长期客户画像。前端历史记录和审计查询不
直接读取 LangGraph 内部表。

### 2.2 第二层：短期对话记忆

PostgreSQL 业务表保存原始用户/助手消息，AgentState 只保留运行需要的紧凑副本：

- 最近若干轮原始消息；
- 一份滚动结构化摘要；
- 摘要覆盖到的最后一个 `message_id`；
- 本轮构造上下文时的 Token 统计。

滚动摘要必须保留：已确认人物、已确认关系、用户目标、重要决定、待解决问题和
未完成任务。摘要不能把模型推断升级为已确认事实。

### 2.3 第三层：长期业务记忆

长期记忆以“事实”而不是整段聊天保存：

- `owner_id`：租户隔离；
- `person_id`：事实所属人物；
- `category` 与结构化 `value`；
- `status`、`version`、`valid_from`、`valid_to`；
- `confidence`；
- 来源消息 `message_id`；
- 是否需要用户确认；
- 被哪条新事实替代。

模型只产生候选事实。确定性代码校验证据、owner 和版本后才能写入。矛盾、敏感或
低置信度事实进入待确认状态，不能直接污染客户画像。

### 2.5、摘要为什么必须结构化

举个连续对话的例子：

> 用户：确认了，他是我同事。但我还没确定他属于哪个部门。

- `confirmed_people`、`confirmed_relations`：目前明确确认的人物和关系。
- `uncertainties`：仍有疑问的内容，不能当作确定事实使用。
- `open_questions`：还需要向用户确认的问题，例如“张三属于哪个部门？”
- `unfinished_tasks`：已经提出但尚未完成的操作，例如“待确认后录入关系”。

校验摘要结构、长度、证据 ID
    ↓
用旧版本、旧游标做乐观锁提交
    ↓
更新摘要正文、版本号和覆盖游标
```

**关键公式是：**

```
新摘要 = 合并压缩（旧摘要 + 新增消息）
```

不是只总结新增消息，也不是每次重新读取全部历史原文。

**情况 A：新增的是50条消息**

为了便于说明，假设已有：

```
V1：覆盖 msg_001～msg_100
游标：msg_100
```

且新增消息已经积累到 `msg_150`，Token 预算允许：

| 本次处理      | 模型输入                       | 提交结果               |
| ------------- | ------------------------------ | ---------------------- |
| 第一批        | V1正文 + msg_101～msg_140      | V2，游标推进到 msg_140 |
| 下一次任务    | 发现 msg_141～msg_150 只有10条 | 不生成，仍保留 V2      |
| 后续再新增2条 | V2正文 + msg_141～msg_152      | V3，游标推进到 msg_152 |

那10条没有丢失，只是保留在原始消息表中，等待达到最小批次。

这里“V1覆盖100条”是沿用你的示意前提；按当前默认40条批次，首次生成的 V1 不会一次覆盖100条。

**情况 B：新增的是50次完整问答**

通常会新增100条消息。

如果这100条已经积累好，有足够后台任务且预算允许，可能分成：

```
40条 → 更新一次
40条 → 再更新一次
20条 → 再更新一次
```

但实际后台边聊天边处理，也可能每积累12条就更新一次。**版本次数由处理批次决定，不固定对应提问次数。**

**摘要正文怎么生成？**

模型收到的材料类似：

```
{
  "previous_summary": {
    "confirmed_people": [
      {
        "text": "张建国是用户的客户",
        "evidence_message_ids": ["真实的旧消息ID"]
      }
    ]
  },
  "new_messages": [
    {
      "message_id": "m1",
      "role": "user",
      "content": "张建国还喜欢钓鱼"
    },
    {
      "message_id": "m2",
      "role": "assistant",
      "content": "已记录他的爱好"
    }
  ]
}
```

本批新消息使用 `m1`、`m2` 等短编号，方便模型正确引用。模型输出七个固定摘要字段，合并重复内容、保留重要事项、移除已解决问题。

代码校验后，把短编号换回真正的 `message_id`，再把完整新摘要存为 `JSONB`。

如果模型调用失败、JSON或证据校验失败，**旧摘要和旧游标保持不变**；后台任务重试时仍从原位置继续。

你阅读时可以抓住三个变量：

```
previous.content                 已有的压缩历史
previous.covered_until_message_id 已处理到哪里
previous.version                 本次提交依据哪个旧版本
```

它们分别解决“保留历史信息”“避免重复摘要”“避免并发覆盖”三个问题。

## **1、如何实现代词指代解析（Anaphora Resolution）**。

### 1.1、 正则表达式

```python
_LEADING_REFERENCE = re.compile(
    r"^\s*(?:那)?(?:他|她|这个人|那个人|这位|那位)(?:的|是|有|和|与|怎么|什么|呢|吗|[？?\s]|$)"
)
```

- **作用**：它用来判断用户的输入是不是以“单数第三人称代词”开头的追问（比如“他呢”、“她喜欢什么”、“那个人是谁”）。
- **设计亮点**：
  - `^\s*(?:那)?`：允许开头有空格，并允许“那”作为语气词（如“那他是谁”）。
  - 紧跟着必须是明确的单数代词（他/她/这个人等）。
  - 后面必须紧跟特定的助词、动词或标点（如“的”、“是”、“有”、“怎么”、“什么”等），或者直接结束/跟标点。这保证了“他”确实是一个作为主语的指代，避免了“他乡遇故知”这种“他”作为构词成分的误判。



### 2.2、提取焦点人物（`derive_focus` 函数）

- **作用**：从**本轮**已经成功执行过的工具调用结果（`tool_results`）中，提取出“焦点人物”。
- **工作流程**：
  - 遍历工具结果，只筛选出与人物相关的工具（`_PERSON_TOOLS`，如查找人物、获取详情等）。
  - 要求状态必须是 `SUCCESS`，且返回的数据中包含有效的 `person_id` 和 `name`。
  - 利用字典 `people` 以 `person_id` 为键进行去重。
- **返回逻辑**：
  - 如果刚好只有 **1** 个成功的人物结果，它会将这个人物作为“焦点”（附带 owner_id、conversation_id 等上下文），返回焦点对象。
  - 如果有 **0 个或多个**，则视为无法确立唯一焦点，返回 `None` 和 `candidates`（候选人列表）。



### 3. 解决指代（`resolve_reference` 函数）

```python
def resolve_reference(state: dict[str, Any]) -> dict[str, Any]:
```

- **作用**：核心决策引擎。根据用户输入和当前状态，决定如何处理代词。
- **返回的三种状态**：
  - **`SKIP`（跳过）**：用户的输入不是指代句（校验不通过），或者输入包含“用户补充：”（可能是系统自动补全的内容，防污染）。直接跳过，交给常规逻辑处理。
  - **`RESOLVED`（已解决）**：状态中存在有效的 `person_focus`，并且它的 `owner_id` 和 `conversation_id` 与当前会话完全一致。系统直接把代词映射为这个焦点人物，继续执行。
  - **`CLARIFY`（要求澄清）**：如果 `person_focus` 没有命中（比如跨会话了，或者上一轮也没确定唯一人物），它会去检查 `person_focus_candidates`（候选列表）。同样，它**强制校验**候选列表必须属于当前的 `owner_id` 和 `conversation_id`。如果符合，最多取前 5 个候选人返回，让上层逻辑向用户反问：“您指的是张三还是李四？”
- **安全边界**：代码多次强调 `owner_id` 和 `conversation_id` 的匹配（`focus.get("owner_id") == owner_id`），这是非常关键的安全设计，防止 A 用户看到 B 用户的人物焦点，也防止跨对话串台。

## 2、为什么要使用SSE

### 2.1、 HTTP 协议 —— 懒惰的服务员

- **交互模式**：客户端主动发起单次请求，服务端被动响应。只能一问一答。
- **核心痛点**：服务端**无法主动推送**消息。如果要获取耗时任务的最新状态，客户端只能不断轮询（Polling）。
- **协议特性**：无状态、单向请求。
- **典型场景**：普通接口查询、网页加载、提交表单等。

### 2.2、 SSE 协议 —— 勤快的服务员

- **全称**：Server-Sent Events（服务器发送事件）。
- **交互模式**：客户端发送一次 HTTP 请求后，服务端会一直保持连接，持续主动推送消息，直到任务结束。
- **协议特性**：**单向（仅服务端 → 客户端）推送，基于 HTTP 协议。**
- **⚠️ 注意事项**：**SSE 只能推送文本数据**，不支持二进制；实现难度中等。
- **典型场景**：大语言模型（LLM）的流式输出、外卖进度、股票数据 K 线图、仪表盘等。

### 2.3、 WebSocket 协议 —— 随身带着对讲机的服务员

- **交互模式**：客户端和服务端**双向通信**，双方都可以主动发起推送。
- **协议特性**：全双工通信。在一定程度上**模糊了客户端与服务端的角色**。
- **典型场景**：聊天室、实时互动场景（如游戏、协同编辑）。

### 2.4、为什么 SSE 受到了关注？（对比 HTTP 与 WebSocket）

SSE 协议受到越来越多的关注，主要是其**完美适配了 AI 大模型流式输出**的场景。

- **场景描述**：客户端发起一个问题之后，服务端流式推送返回大模型生成的内容。
- **为什么不用 HTTP？**
  - HTTP 只能等大模型完全生成了全部答案，才能一次性返回全部内容，导致**等待时间太长**（首字延迟高）。
- **为什么不用 WebSocket？**
  - **成本高**：WebSocket 是全双工通信，需要维护复杂的连接状态。
  - **需求不匹配**：在 AI 对话场景中，一般是等待大模型回答完一个问题之后再问下一个，**客户端没有主动发起对话的需求**。SSE 这种单向推送（Server -> Client）恰好完美匹配。



## 3、深入了解 SSE 协议

### 3.1 通过 SSE 协议交互过程

1. 客户端通过普通的 **HTTP 请求**连接服务器。
2. 服务器返回一个特殊的响应类型（事件流）：`Content-Type: text/event-stream`。
3. 这个 HTTP 连接**不会马上结束**。
4. 服务器可以在这个连接里不断写入事件数据。
5. 浏览器通过 `EventSource` 接口持续接收这些消息。

**响应头示例（区别于普通 HTTP 的 `application/json`）：**

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream  # 事件流，表示流式返回
Cache-Control: no-cache          # 禁用缓存
Connection: keep-alive           # 长连接，保持链接，服务器好持续推送
```

### 3.2 数据内容与消息格式

**客户端请求示例：**

```http
GET /api/chat/stream?message=请解释一下SSE是什么 HTTP/1.1
Host: example.com
Accept: text/event-stream
```

**SSE 消息格式：**
格式非常简单，包含以下 4 个字段，**每条消息用一个空行结束**：

| 字段    | 说明                                                    |
| :------ | :------------------------------------------------------ |
| `data`  | 消息内容，也就是具体的数据（如 LLM 返回的文本片段）。   |
| `event` | 事件类型，可自定义事件类型（如 `message`, `done` 等）。 |
| `id`    | 消息 ID，用于断线重连后续传。                           |
| `retry` | 重连间隔，单位毫秒。                                    |

**LLM 流式输出数据示例：**

```
event: message
data: {"delta":"SSE "}

event: message
data: {"delta":"是一种"}

event: message
data: {"delta":"基于 HTTP "}

event: message
data: {"delta":"的服务器"}

event: message
data: {"delta":"推送技术，"}

event: done
data: [DONE]
```

### 3.3 如何标识传输结束？

**SSE 协议只规定了消息格式，没有规定结束时必须发送某个标识码。** 通常有以下 4 种方式：

- **方式 1**：发送结束后，**连接自动断开**。

- **方式 2**：发送**自定义结束事件**。

  ```
  event: done
  data: {}
  ```

- **方式 3**：发送**自定义结束消息**。

  ```
  event: done
  data: [DONE]
  ```

- **方式 4**：发送**业务状态字段**（在数据中带标志位）。

  ```
  event: chat
  data: {"delta":"最后一段内容","finished":false}
  
  event: chat
  data: {"delta":"","finished":true}
  ```

## 4、Python实现SSE

```python
from fastapi import FastAPI
from sse_starlette.sse import EventSourceResponse
from pydantic import BaseModel
import uvicorn
import asyncio
import json
app = FastAPI(title="对话Agent")
class ChatRequest(BaseModel):
    message: str
class MockLLM:
    async def astream(self, message: str):
        tokens = ["你", "好", "，", "这是", "一个", "流式", "输出", "的", "测试", "。"]
        for token in tokens:
            await asyncio.sleep(0.2)
            yield {"type": "message", "delta": token}
        yield {"type": "_done"}
LLM = MockLLM()
@app.post("/api/chat/stream")
async def chat_stream(req: ChatRequest):
    async def event_generator():
        async for ev in LLM.astream(req.message):
            if ev.get("type") == "_done":
                # 发送结束事件，通知客户端流结束
                yield {"event": "done", "data": "[DONE]"}
                return
            # 把每个数据块序列化成字符串，sse-starlette 会帮你加上 "data: " 前缀
            yield {"event": "message", "data": json.dumps(ev, ensure_ascii=False)}

    return EventSourceResponse(event_generator())

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8080)
```

### 4.1、yield 让函数变成生成器

普通函数 `return` 一次就结束。
带 `yield` 的函数，每次调用到 `yield` 就**暂停并产出一个值**，下次再从这里继续。

```python
def gen():
    yield 1
    yield 2
    yield 3

for x in gen():
    print(x)   # 1, 2, 3
```

关键点：**函数体不是一次性执行完，而是每次产出一个值就暂停，等下一次被迭代时再继续。**

### 4.2、 在这段代码里 `yield` 干了什么？

```python
async def event_generator():
    async for ev in LLM.astream(req.message):
        if ev.get("type") == "_done":
            yield {"event": "done", "data": "[DONE]"}
            return
        yield {"event": "message", "data": json.dumps(ev, ensure_ascii=False)}
```

- `LLM.astream` 每吐一个 token，`event_generator` 就 `yield` 一个 SSE 事件。
- `EventSourceResponse` 拿到一个事件，立即通过网络推给前端，然后回来继续迭代下一个。
- 直到 `return`，生成器结束，连接关闭。

**如果没有 `yield`，就只能等所有 token 生成完，一次性返回，流式效果就没了。**

### 4.3、 `async` + `yield` = 异步生成器

`async def` + `yield` 组合，就是**异步生成器**：

- 它可以被 `async for` 遍历。
- 它可以在产出值之间 `await` 异步操作。
- 它不会阻塞事件循环。

这正是 SSE 需要的：**边等 LLM 生成，边往客户端推，且不阻塞其他请求。**

### 2.4、（面试话术）设计一个合理的Function Call？

你面试时可以这样概括：

> 一、开场回答：先讲清楚 Function Calling
>
> 如果让我设计 Function Calling，我会先把它拆成一个完整闭环：给模型提供工具定义，包括名称、描述和参数 Schema；模型根据用户意图生成结构化调用请求；应用侧校验参数、权限和执行条件；执行工具后，把结果按调用 ID 返回给模型；模型再决定继续调用工具还是回答用户。这里有一个基本边界：模型负责提出调用意图，应用负责决定是否执行，以及怎样执行。工具描述中的“需要授权”不能代替服务端权限检查，模型生成了合法 JSON，也不代表这次操作在业务上合法。在此基础上，我参考 OpenClaw 的工具目录和按需发现思想，设计了一套适合较大工具集合的方案。
>
> 我的出发点是：当系统接入很多业务工具和 MCP 服务时，把所有工具的完整 Schema 放进每次请求，会增加上下文占用，也会让模型在大量相似工具之间做选择。
>
> 因此，我把“工具已经接入运行时”和“工具定义已经展示给模型”分开处理。对于当前任务经常需要的少量工具，直接展示完整 Schema；对于数量较多、使用频率较低的工具，先保留在服务端目录中，通过 search、describe、call 三个操作按需访问。模型先搜索能力，获得少量候选；参数不明确时，查询准确 Schema；最后通过工具 ID 调用。所有调用仍经过统一执行器，权限、校验、超时和审计都不会因为工具被隐藏而绕开。
>
> 我关注的效果也不只是初始 token 减少，而是完整任务的成功率、总 token、模型往返次数和延迟。按需发现会增加步骤，所以小工具集合我会保留直接调用，只有在实际任务中收益成立时才启用。
>
> 二、架构展开：我怎样划分系统职责
>
> 我的方案分成五个职责清晰的部分。
>
> 1. 工具注册与适配
>
> 这一层负责把本地函数、业务 API 和 MCP 工具适配成统一工具定义。
>
> 统一定义至少包括：
>
> - 稳定的工具 ID。
> - 名称和能力描述。
> - 输入 Schema。
> - 执行入口。
> - 来源及必要的执行策略。
>
> 对于 MCP，我获取服务器提供的工具定义，再构建本地执行代理。模型调用代理时，实际通过 MCP 客户端访问服务器。这类似我熟悉的 Java RPC：接口元数据和本地代理留在应用中，真正的能力由服务端提供，不需要把远端实现复制进项目。工具 ID 要区分来源和所属服务，不能只使用容易重名的函数名。执行时也不能让模型直接传一个任意 URL 或函数路径，而应该解析到注册表中已经存在的执行入口。
>
> 1. 当前会话的有效工具目录
>
> 注册表表示系统接入了什么，有效目录表示当前用户、当前会话能使用什么。我会先根据用户身份、业务范围和工具策略过滤，再建立可搜索目录。这样用户无权使用的工具，不会通过搜索结果暴露出来。搜索时过滤还不够，执行时仍然要重新检查，因为工具可能被禁用、权限可能变化，或者会话已经结束。如果一次操作需要等待人工审批，审批结束后也要重新确认执行条件，而不是拿着审批前的判断直接执行。
>
> 1. 模型可见的工具入口
>
> 工具较少时，直接发送业务工具 Schema。
>
> 工具较多时，模型主要看到：
>
> - 少量常用工具。
> - search：发现能力。

# 1、BM25 原理解析

## 1.1、BM25 的核心公式

BM25，全称 Best Matching 25，是一种基于**词频统计**的文本检索排序算法，核心思想可以归纳为一句话：**根据查询词在候选文档中出现的频次和稀有程度，给每个文档打一个相关性分数，按分数从高到低排序返回**。

公式这里我不用背全部，核心结构：

```
BM25(D, Q) = Σ IDF(t) × [ tf(t,D) × (k₁+1) / (tf(t,D) + k₁ × length_norm ) ]
```

## 1.2、BM25解决什么问题（面试）

公式看起来复杂，拆开来看其实就解决三个问题：

### 1.2.1、**TF 饱和（解决词频线性膨胀）。** 

TF-IDF 里你一个词出现 100 次，得分就是出现 1 次的 100 倍，这显然不合理——一篇文档把"Python"写 1000 遍不等于它是 1000 倍相关。BM25 用了一个饱和函数：`tf × (k₁+1) / (tf + k₁)`。当 `k₁=1.5` 的时候，词频从 1 到 5，得分涨得很快；但从 10 到 100，得分基本不涨了——说明这个词"已经够了"，再重复没意义。

### **1.2.2、文档长度归一化（解决长短文档不公平）。**

一篇 100 页的论文和一篇 1 页笔记，同时包含"Python"3 次，TF-IDF 认为一样相关，但实际上短文档中"Python"更集中，应该更相关。BM25 通过 `length_norm = 1 - b + b × (doc_len / avgdl)` 来惩罚长文档。`b=0.75` 是一个折中值，`b=0` 不惩罚，`b=1` 完全按比例惩罚。

### 1.2.3、**IDF 逆文档频率（解决常见词权重过高）。** 

这个和 TF-IDF 一致——"的"、"是"这类词几乎每篇都有，IDF 接近 0，权重自然压下去了；而"Mamba"、"RLHF"等专业术语只在少数文档出现，IDF 很大，匹配上了就是高权重。

## 2、为什么要用 BM25？（三个层面）

**第一，算法层面——比 TF-IDF 好。** BM25 修复了 TF-IDF 的两个致命问题：词频线性膨胀和文档长度缺失。实践中 BM25 的检索效果显著优于 TF-IDF，这是经过大量 IR（信息检索）实验验证的。

**第二，工程层面——零成本上手。** BM25 是**无监督、免训练、纯统计**的算法。你不需要 GPU，不需要标注数据，不需要微调模型，丢进一个文档集，立刻就能搜。做 RAG 系统时，BM25 可以作为一个强 baseline、兜底方案，甚至实际线上的一部分。

**第三，架构层面——和向量检索互补。** 现在做 RAG 的主流方案是混合检索。向量检索（embedding + 向量数据库）解决的是**语义匹配**问题——"汽车"能匹配到"轿车"；而 BM25 解决的是**精确关键词匹配**——搜"GIL"就是"GIL"，不会被模糊掉。两者各有所长：

## 3、BM25 的优缺点

### 优点

1. **简单高效**：纯统计，不需要模型，几行代码就能实现，检索速度极快（倒排索引 O(词数)）。
2. **可解释性强**：每个词的贡献透明，你可以精确知道为什么某篇文档排前面——用户问"为什么推荐这篇？"你可以回答"因为它命中了 X、Y、Z 三个关键词"。
3. **精确匹配能力强**：对于代码、API 名称、错误码、专有名词这类不能模糊匹配的词，BM25 比向量检索可靠得多。
4. **冷启动友好**：不需要训练数据，新文档加入后重建索引即可，适合快速原型和动态语料库。
5. **成熟稳定**：从 1994 年提出至今近 30 年，工业界大量验证，Lucene/Elasticsearch 内置实现，生产级别可靠。

### 缺点

1. **词汇鸿沟（Vocabulary Mismatch）**：这是最致命的。查询说"轿车"，文档写"汽车"，BM25 完全不认为它们匹配——因为它只看表面字符，不理解语义。这也是为什么需要向量检索来补位。
2. **词序和上下文忽略**：BM25 是纯粹的词袋模型（Bag of Words），"人工智能"和"智能人工"对它来说是一样的，它完全不理解语法结构和上下文关系。
3. **不适合长查询**：当查询是一大段话而非几个关键词时，BM25 效果会明显下降，因为它不对查询端做任何语义理解。
4. **OOV（Out of Vocabulary）问题**：没有语义泛化能力，没见过的词的变体（如复数、时态、拼写错误）完全无法处理，需要靠预处理（分词、词干提取）来缓解。
5. **超参数敏感**：k₁ 和 b 一般取 Lucene 默认值（1.5, 0.75）就还行，但在特定领域（短文本 vs 长文档、不同语言）需要调参才能达到最佳效果。

### 4.3、调参思路

#### Level 1：无标注数据 → 按场景选默认值

| 场景                     | k1      | b        | 原因                                |
| ------------------------ | ------- | -------- | ----------------------------------- |
| 短文本（标题/Tweet/FAQ） | 0.5~1.0 | 0~0.3    | 出现 1 次即强信号，长度差异小       |
| 通用搜索（新闻/博客）    | **1.2** | **0.75** | Lucene 默认，久经考验               |
| 技术文档/论文            | 1.5~2.0 | 0.5~0.75 | 多次提及 = 深入讨论，应奖励         |
| 代码搜索                 | 0.3~0.8 | 0~0.3    | 函数名出现 1 次就够，重复无意义     |
| 中文文档                 | 1.0~1.5 | 0.5~0.75 | 中文词频分布更均匀，适度降低 k1     |
| 混合检索（+向量）        | 1.0~1.2 | 0.5~0.75 | BM25 只需做关键词锚定，不必极致精确 |

#### Level 2：有标注数据 → 网格搜索

如果有标注好的 (query, relevant_docs) 数据，直接网格搜索：

```
k1_candidates = [0.3, 0.8, 1.2, 1.5, 2.0, 3.0]
b_candidates  = [0.0, 0.3, 0.5, 0.75, 1.0]

for k1, b in product(k1_candidates, b_candidates):
    bm25 = BM25(corpus, k1=k1, b=b)
    ndcg = evaluate(bm25, test_queries)   # 用 NDCG 或 MRR
    record(k1, b, ndcg)
```

**评估指标选择：**

- **NDCG@k**：你关心 top-k 的排序质量（推荐场景）
- **MRR**：你只关心第一个正确答案排第几（问答场景）
- **Recall@k**：你只关心相关文档有没有被捞回来（RAG 召回阶段）

我的项目是一个基于 LangGraph 的人际关系助手，支持人物资料维护、关系维护和查询。

意图识别最初只输出一个意图标签，后来为了支持一句话包含多个业务请求，我把它改成了“生成结构化业务目标”。

例如用户说：“添加一个客户张三，他出生于1998年，再查询李四的资料。”系统需要识别出三个目标：保存张三的人物资料、建立客户关系、查询李四资料。其中客户关系依赖人物资料目标，查询李四则是独立目标。

实现上，我使用 LangChain 的 with_structured_output，结合 Pydantic 定义输出契约。每个目标包含固定的 intent、目标描述、用户原文证据、前置目标，以及结构化的人物或关系信息。

模型负责提出目标草案，服务端代码负责校验。校验包括：目标数量限制、原文证据是否来自当前输入、依赖是否指向前面的目标，以及人物属性是否被明显错误地拆成独立更新目标。目标 ID 由服务端生成，模型不能自行指定。

分类器使用当前请求和受控的对话上下文；长期客户事实不会直接进入分类器，减少无关信息干扰。

如果输出没有通过结构或业务校验，系统会把具体错误反馈给模型，最多修复一次。这次修复也消耗原请求的模型调用和 Token 预算。两次都不合法，就明确结束请求，不把内部识别错误转成无限重试。

识别通过后，LangGraph 根据目标类型进入提取、规划或澄清节点，再按目标依赖顺序调度。工具规划使用与执行校验相同的工具白名单，防止“查询目标夹带写入”或“人物目标夹带关系操作”。

最后，目标是否完成由真实工具回执判断，不由模型自行宣布成功。因此，我把自然语言理解交给模型，把依赖、操作范围和完成条件留在确定性代码里。

## **1．当前意图识别是怎么做的**

先区分三个概念：

| 概念                  | 回答的问题         | 例子                           |
| --------------------- | ------------------ | ------------------------------ |
| 意图 `intent`         | 属于哪类操作？     | `ADD_PERSON`：新增人物         |
| 目标 `goal`           | 具体要完成什么？   | 保存张三的姓名、职业、出生年份 |
| 工具计划 `tool_calls` | 用哪些工具完成它？ | 查找人物 → 新增或补充资料      |

**一个目标可以调用多个工具；一句话也可以包含多个目标。**

比如：

> 我有个客户叫张三，他是销售经理，出生于1995年。

按当前设计，应拆成：

```
目标 0：ADD_PERSON
        保存张三的资料，包括职业、出生年份

目标 1：ADD_RELATION
        建立“本人 → 张三”的客户关系
        依赖目标 0
```

这里“出生于1995年”属于人物属性，不应该单独拆成更新目标。

具体处理过程如下：

**① 准备输入。**

分类节点从 `state["model_context"]` 选择上下文，剔除长期记忆块，并追加当前用户原文。

当前提问是本次操作的依据；历史用于辅助理解，例如理解“他”指谁。

**② 给模型业务规则。**

[classify_intent.py (line 29)](D:/WorkSpace/Deepseek-harness/WorkSpace/ai-relationship-assistant/backend/agent/nodes/classify_intent.py:29) 中的提示词规定：

- 最多四个目标。
- 新人物及其属性放在一个目标里。
- 人物关系单独建目标。
- 目标必须提供用户原文 `source_quote`。
- 依赖只能指向更早的目标。
- 不支持的需求使用 `UNSUPPORTED`。
- 意图不明确时使用 `UNCLEAR`。

**③ 通过结构化输出得到目标草案。**

核心调用是：

```
batch = invoke_structured(
    IntentBatch,
    prompt,
    messages,
    validator=lambda value: build_goals(
        value, state, require_business_fields=True
    ),
)
```

模型返回的结构类似：

```
{
  "goals": [
    {
      "intent": "ADD_PERSON",
      "description": "保存张三的人物资料",
      "source_quote": "我有个客户叫张三，他是销售经理，出生于1995年",
      "depends_on": [],
      "person": {
        "name": "张三",
        "occupation": "销售经理",
        "birth_year": 1995
      }
    },
    {
      "intent": "ADD_RELATION",
      "description": "建立本人和张三的客户关系",
      "source_quote": "我有个客户叫张三",
      "depends_on": [0],
      "relation": {
        "person": "张三",
        "related_to": "当前用户",
        "type": "客户"
      }
    }
  ]
}
```

项目复用了 LangChain 的 `with_structured_output`。默认使用 Function Calling 来承载这个结构。

**这里的 Function Calling 是让模型输出 `IntentBatch`，不会直接执行新增人物等业务工具。**

**④ 代码检查模型有没有违反规则。**

`IntentBatch` 的 Pydantic 定义检查字段、类型、意图枚举和数量等。

`build_goals()` 再检查业务约束：

- `source_quote` 是否确实出现在当前输入中。
- 是否出现完全重复的意图与描述。
- 依赖下标是否合法、是否只指向前面的目标。
- 人物或关系目标是否保留必要的结构化字段。
- 是否出现已知的“创建属性被错误拆成更新目标”的情况。

然后，服务端生成 `goal_id`，把依赖下标转换为目标 ID，初始化目标状态。

**这些规则能发现明确的错误，但不能证明模型已经完整、准确地理解所有自然语言。** 原文存在，也不等于模型对原文的解释一定正确。

**⑤ 校验失败时有限修复，通过后才缓存。**

`invoke_structured()` 会把错误代码、具体规则和被拒绝的候选反馈给模型，允许一次修复。

只有结构和业务校验都通过，结果才作为成功结果缓存。修复也消耗请求预算。

两次候选仍不合法时，系统结束本次解析，不开始工具操作。它不会把内部模型错误无限交给用户澄清。

**⑥ 写入状态，交给目标调度。**

```
return Command(
    update={"goals": goals, ...},
    goto="validate_goals",
)
```

随后 `select_next_goal()` 选择依赖已经满足的目标：

- 人物、关系新增或修改：进入 `extract_info`。
- 查询、删除等：进入 `plan_tasks`。
- `UNCLEAR`：进入澄清中断。
- `UNSUPPORTED`：记录失败。
- 没有剩余目标：汇总回复。

**注意：当前 V2 不使用“置信度低于 0.6 就澄清”的逻辑。** 那是同一文件下半部分的旧版本分支。V2 的 `intent_confidence=0.0` 是兼容字段，不代表识别结果可信度为零。

# Day12-2026-10-11日（Function Calling）

## 1、（面试话术）项目中怎么做的Function Calling？

我当前项目中设计了三种模式的functtion calling，direct模式、plan模式、discover模式：
第二种plan模式，我设计了一个ToolPlan的schema，这个ToolPlan直接定义为实现当前目标所需的所有工具执行链路、步骤。例如：用户提问：我有个朋友叫张三。要实现这个目标需要分为3步，查询有没有“张三”这个用户，如果没有这个用户再新增用户，新增用户后还需要拿着新增的用户ID，新增一个关系。在plan模式下，LLM直接返回一个List对象，分别是查询人物、新增人物、新增关系，这样会存在一个附加问题：第3个工具的参数依赖第2个工具的返回值，对于这样的依赖关系，我的解决方案是，为每个tool_call生成一个step_id，该step_id是放在ToolPlan的schema中，由LLM生成的本次tool_call中唯一id，还会生成一个depends_on参数记录依赖哪个工具的step_id，如果参数也有依赖，我使用了一个固定引用格式"$ref"作为替换，一个key-value的格式，key为$ref，value为一个字典保存step_id返回值的哪个数据。后端拿到tool_calls后依次执行任务，**如果查到有“张三”这个用户 → 复用人物 ID ，如果未找到目标   → 新增人物，如果有多个人物 → 执行中断让用户澄清，如果查询系统故障 → 不能把故障当作“人物不存在”而继续执行后续操作。**

还有就是LLM对当前登录用户的id处理，因为LLM的输出需要看做一个不可置信输出，当前登录用户ID绝对不允许由LLM输出，例如用户提问：我有个朋友叫做张三，此时新建张三这个用户需要获取owner_id，需要获取当前登录用户。所以我的设计方案是，在提示词中写清楚，如果涉及到”本人“、”当前用户“将ID替换为特殊字符”$self“，服务端在拿到function_call后进行解析，手动将$self替换为当前用户ID。

### 1.1、面试官如果追问为什么要设计plan模式？

​	我回答：
​		1、首先是因为我的项目中一般对人物做修改往往也会同时修改关系，频繁的出现第二个工具的入参依赖第一个工具的返回值，所以我想进行优化，一次性地让LLM给到tool执行逻辑，而不是执行一次，返回一次，减少对LLM的调用次数，**代价是需要维护工具输出契约，而且提前规划可能与实际结果不一致，因此仍保留观察、澄清和重规划。**

​		2、**第二个原因是plan模式会首先识别用户的意图，而具体的意图调用工具的范围是能够确定的**，我举个例子：用户可能提问，帮我请个假，这句话的意图大模型能识别为“创建流程”，而创建流程只能调用流程相关的工具，如果哪天大模型出现幻觉返回了一个财务相关的工具，plan模式下能在代码层面发现问题，而不是到执行那一步才发现问题，利于审计。

​		3、第3个原因**是能省token，因为减少了对LLM的调用次数。plan 更适合流程明确、对审计要求很高的业务场景；而结果强烈影响后续路线、需要探索的任务，Direct 可能更合适。遇到无法预先确定的分支，Plan 仍然需要观察、澄清或重规划。**

### 1.2、面试官继续追问，省了多少token？

我是用同一批测试用例分别进行测试的，仅function call这一个步骤，消耗token的中位数相较于direct模式降低了40%左右。

### 1.3、面试官继续追问，这个模式是否有问题？

我回答：实际开发过程中确实有遇到问题，最常见的问题这个模式除了给到函数定义schema，还需要把工具返回值给列出来，这样LLM在处理工具依赖的时候才能准确列出哪个参数依赖具体哪个返回值。这其实也间接导致了token消耗增多。而且仅仅在提示词中写好返回值也不够，LLM仍然可能返回错误的引用，所以当有引用的时候还需要在服务器代码层面进行校验，项目复杂度更高。

## 1、（面试话术）工具调用失败有几种？分别是怎么处理的？

### 1.1、工具选择出错

​	首先定义工具的时候就应该明确，工具名称一眼就能区分用途，描述要写清楚适用场景和不适用场景，参数要标明参数类型必填项（参数也可以写描述，描述这个参数代表什么含义）。如果真的有相似的工具，每个工具应该树立明确的使用边界，将使用示例列出来放入提示词中。而且只有提示词优化解决还不够，这样的场景遇还需要在后端做校验，需要在代码层面判断当前的业务场景，大模型选择的工具是否正确。

### 1.2、参数不正确

​	我首先是在工具定义中描述好每个工具的json schema，包括到每个参数的名称、类型、取值范围都详细描述在提示词里，给到大模型明确的定义。然后在代码层面使用了Pydantic来做类型检查的，我定义好每个工具的参数实体类，使用了forbid（/fərˈbɪd/）模式进行校验，这个模式会明确校验所有的参数名称、类型、取值范围，并且不允许多传入参数。

​	如果校验不通过，会抛出异常。我对此类异常的处理逻辑是：类型、参数、工具名称等错误允许大模型重新生成一次，我在代码层面try-expect异常，然后使用Command命令重新跳转到规划节点，在state中记录失败原因、重试次数，让大模型重新生成的时候也会在提示词中附带错误原因：某个工具哪个参数有具体什么问题。

​	准确的说我做了四层校验：第一层是校验是不是json格式，如果LLM返回的格式就有问题也自然不需要执行后续逻辑。第二层是校验工具名称，名称必须是真实存在的工具，避免大模型幻觉出来的工具名称，还有就是检查是否出现明显异常的工具调用。例如：如果用户的意图是查询订单，那就应该调用和订单相关的工具，不可能调用出现支付工具吧，避免明细错误的工具调用。第三层是参数校验，就是我刚刚说的使用pydantic的forbid模式。第四层校验是清洗不安全的参数，例如当前用户或者是是否需要人工介入标志，此类参数不能由大模型生成，我在项目中让大模型使用关键字标识此类不安全的参数，后端再校验是否有关键字，再把关键字替换成对应的id。

> Pydantic有三种模式：
>
> | 取值       | 行为                 | 是否报错                 | 额外字段是否保留                |
> | :--------- | :------------------- | :----------------------- | :------------------------------ |
> | `"forbid"` | 禁止传入未定义的字段 | 是，抛 `ValidationError` | 不保留                          |
> | `"allow"`  | 允许传入未定义的字段 | 否                       | 保留，可通过 `model_extra` 访问 |
> | `"ignore"` | 忽略未定义的字段     | 否                       | 不保留，直接丢弃                |

### 1.3、越权错误，选到了不应该选到的工具

​	首先确认权限的范围，是按照agent，还是当前登录的用户能调用哪些工具进行划分？在拼接tools的时候，就需要校验一次权限，只把有权限的工具展示给大模型，大模型给到tool_call后，也需要再次校验，校验大模型返回的工具是否在权限范围内。

### 1.4、工具执行报错

​	首先我的项目中工具调用是做了幂等的，我会根据当前用户的userid、reqeustid、工具名称取hash值，生成一个call_id，详细参考Day2的第6点。把工具的错误原因进行分类，对不同的错误类型有不同的处理方案。

​	如果要具体描述，我有执行工具节点，工具节点只负责执行工具，把工具执行结果生成一个结构化的对象，包含是否成功、失败编码、失败信息等等，然后流转到观察节点后，根据结构化的信息再进行判断下一步。如果是direct模式下，观察节点会对错误编码进行整理信息，我根据错误编码还做了紧急程度的分类，例如：**如果是越权操作，例如当前账号没有权限，那都不需要再让大模型参与了直接给反馈结束。如果是网络异常，数据库连接失败，可以不经过大模型直接重试一次，如果是数据格式错误、没有查询到数据可以把错误信息放进提示词，让大模型重新规划一次。如果是查询到多条数据，那就需要人工介入了，让用户选择。**

​	我举个例子：新增用户前需要查询有没有该用户，如果没有查询到用户，执行工具会记录错误信息NOT_FOUND，如果是direct模式下，观察节点会对错误编码进行整理信息，让大模型分析下一步。

如果是A执行成功，B执行失败，重试也失败的场景，需要区分是怎样的异常情况：

- 网络暂时不可用：适合稍后继续执行 B。-->显示网络中断的错误信息并进行中断，提示用户隔一段时间再继续执行。（涉及幂等）
- 参数缺失：需要补充信息，直接重复调用没有意义。-->显示参数异常信息并进行中断
- 业务拒绝，例如库存不足：通常需要终止业务并处理 A。-->TCC分布式事务模式，调用A工具的cancel方法。或者是Sega模式。
- 请求超时：B 可能已经成功，只是结果没有返回，必须先核对业务回执。
