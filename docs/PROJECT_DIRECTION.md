# AI 人际关系助手：项目方向与一个月路线

> 更新日期：2026-09-21。本文记录本轮已经确定的目标和设计边界，是当前开发方向的主要依据。
> 当前状态：已有初版代码；本文描述的是下一阶段目标，不代表功能已经实现或测试通过。

7. 当我想增加新技术时，先回答：它解决了哪个已经观察到的问题？如何验证它有用？

## 3. 产品定位与使用者

**定位：具备客户记忆、证据检索和常见关系推导能力的销售沟通 Agent。**

面向需要记住客户背景、整理往来记录、准备沟通的新手销售。先覆盖跨行业共有的关系维护需求。建议主要来自客户历史与档案，本月不依赖专业行业知识库或成熟销售话术库。

“帮助新人达到成熟销售水平”是长期愿景。本月可验证的目标是：减少信息遗忘，使沟通准备能够回到原始记录核对。当前使用模拟数据，不能据此声称真实销售业绩提升。

### 主演示场景

1. 登录账号 A，导入一组明确标记为模拟数据的聊天记录。
2. 系统识别人物、提取事实，保留来源原文、时间与数据归属。
3. 提问：“明天要联系张总，帮我回顾他的情况，建议怎么开场。”
4. 存在同名人物时先选择；明确身份后检索有效资料和有关聊天。
5. 输出客户概况、两三条沟通建议及证据引用；点击引用能看到属于 A 的原始记录。
6. 补充：“之前记错了，喜欢钓鱼的是李总，不是张总。”
7. 查看更正记录，再次提问，确认旧事实不再被当作当前事实。
8. 换账号 C，验证 A 的人物、记忆、对话和引用均不可访问。
9. 展示常见堂兄弟称谓推导，并解释缺少性别或年龄信息时的行为。

## 4. 本月范围

| 必须交付 | 完成标准 |

| 用户独立的私人资料空间 | 身份来自服务端认证，所有读写与检索受归属约束 |

| 有依据的沟通建议 | 引用合法且相关的原文，区分事实与建议，资料不足时说明缺口 |

## 5. 数据模型：账户、人物与资料归属

| 对象 | 语义 | 关键约束 |
|---|---|---|
| `User` | 登录账户 | 用户 ID 唯一；保留现有 Neo4j 账户存储 |
| `Person` | 某个用户维护的人物档案 | 每个档案具有 `id` 和 `owner_id`；姓名不唯一 |
| `self_person_id` | 当前账户在自己图中的本人档案 | 只能指向同 owner 的 Person；不能拿 `user_id` 当 Person ID |
| `Relation` | 两个人物档案间的关系事实 | 两端人物、关系及可选中间人属于同一 owner |
| 原始消息 | 聊天或用户补充的原文 | 记录 owner、来源、说话人、时间和稳定 ID |
| `MemoryFact` | 从证据中整理出的事实 | 记录 owner、人物、属性、来源、状态与版本 |
| 会话与检查点 | 用户同 Agent 交流的运行状态 | thread 归属于登录用户；thread ID 本身不是权限凭证 |

### A、B、C 的例子

A 的账号中可以有 A、B、C 三份 Person 档案，`owner_id` 都是 A 的账户 ID。C 注册自己的账号后，有 C 空间中的本人节点；C 录入朋友 B 时，在 C 的空间创建或选择 B 的档案，再建立关系。

A 空间中的 B 与 C 空间中的 B 可以描述同一个现实人物，但它们是两份独立维护的资料。C 不会因为自己的名字出现在 A 的图中而自动获得 A 的资料。姓名相同也不能作为跨空间认领依据。

既有数据迁移时先审计和备份。旧图中的本人档案若无法唯一识别，由用户明确选择；不要按手机号显示名或姓名猜测关联。

## 6. 记忆如何工作

保留三层：原始记录、有效事实、检索索引。向量索引是派生数据，原文与事实才是依据。

- 提取只生成候选事实，写入前检查结构、人物归属及引用原文。
- 用户明确更正时，保留旧版本并标记失效；含糊矛盾进入待确认状态。
- “这周没空钓鱼”不能自动更正为“不喜欢钓鱼”。时间性事项和长期偏好分开处理。
- 不依据“模型自报置信度”直接覆盖已确认信息。
- 检索先限定 owner 和目标人物，再结合语义、时间与事实状态选择上下文。
- 引用旧聊天时必须说明历史状态，不能把已被更正的陈述重新输出为当前事实。
- 重复导入采用稳定来源 ID 或完整批次哈希去重；不能仅按句子内容去重，避免删除真实的重复发言。
- 索引失败标记为待同步。重试读取最新事实版本；查询时回查权威记录，过滤已失效内容。

## 7. Agent 的责任与执行边界

主流程：理解任务 → 选择工具 → 参数校验与授权 → 执行 → 读取结果 → 继续、澄清、等待确认或回答。

固定导入和校验采用确定流程；检索与沟通准备允许根据结果进行有限的下一步决策。先做单 Agent。

- 模型看不到也不能决定 `owner_id`、登录身份和确认授权。
- 工具返回统一结构，错误按类型处理，而不是匹配中文错误文案。
- 查询结果中的人物 ID 可以供后续工具使用，名字不是稳定引用。
- 删除和明确覆盖通过服务端待确认动作处理，确认绑定用户、会话、动作和参数。
- 超时、取消、工具失败和轮数耗尽都要形成可理解的结果。
- 重复操作不重复产生写入；检查点恢复也要遵守这个约束。
- 原始聊天是数据，其中的“忽略规则”“查看其他用户资料”等文本没有控制系统的权限。

## 8. 常见称谓：明确支持范围与不确定结果

首批清单：父母、祖父母及外祖父母、兄弟姐妹、叔伯姑舅姨、堂表兄弟姐妹、配偶、子女，以及这些路径中的直接常见配偶称谓。以测试清单为范围依据，不用“三代”一词替代具体定义。

必过案例：

```text
A ─父亲→ B ─弟弟→ C ←父亲─ D
```

约定：`X ─父亲→ Y` 表示 Y 是 X 的父亲。沿 C 到 D 逆向走，D 是 C 的子女。D 为男性时，再比较 D 和 A 的年龄，得到堂哥或堂弟；D 为女性时对应堂姐或堂妹。

- 反向“父亲”是“子女”，依赖子女节点性别；不能固定映射为儿子。
- 反向“儿子”是“父母”，依赖当前指向的父母节点性别；不能固定映射为父亲。
- 叔伯年龄顺序不能推出两人子女的年龄顺序。
- 年龄不足或只有同年出生信息时，保留候选称谓并说明缺口。
- 先限制为亲属关系，再寻找有限候选路径；朋友、同事等短路径不能遮住亲属路径。
- 多条路径矛盾时返回冲突；仅扫描部分候选时标记截断，不能声称得到了唯一完整结论。
- 首版关闭自动“大/二/三/小”排行前缀推断，只有用户明确提供且验证了排行含义时再启用。
- 支持范围之外返回“不支持或信息不足”；不让模型兜底产出看似确定的称谓。

## 9. 技术职责与部署边界

沿用 FastAPI、LangGraph、Neo4j、ChromaDB 和现有前端。Neo4j 保存账户、人物、关系和事实；SQLite 保存单实例作品的原始消息、会话及检查点；ChromaDB 保存可重建索引；Langfuse 记录开发者需要的调用信息。

SQLite 适用于本月单实例展示。多实例部署、写入并发或运维需求出现后，再评估 PostgreSQL；迁移要说明解决的问题。不同存储之间不宣称全局原子性，使用幂等键、状态记录、权威数据回查与可重试投影。

优先锁定当前可用依赖组合，先用最小示例验证持久化、工具调用与追踪兼容性。项目当前固定的 LangGraph 为 0.2.61，不能直接照搬最新版文档的所有导入路径与接口。以 `pyproject.toml` / `uv.lock` 作为主要依赖来源，再同步其他安装说明。

## 11. 评测与“完成”的定义

第一周先准备 15 个代表案例，逐步扩展到 60～100 个测试及评测案例。先编写事实与时间线，再编写模拟聊天。保留一组不参与提示词调整的评测数据，按查询时点截断可见信息，避免未来信息泄漏。

评测覆盖：任务完成、同名澄清、事实提取与更正、引用是否支持结论、跨用户隔离、重复导入、故障、反向亲属边及年龄未知。确定性规则用断言，建议质量用明确量表和人工抽查。

性能报告记录数据规模、模型/提示词/代码版本、运行环境、样本量、并发数、失败率、响应时间中位数与 P95、调用次数及 Token 用量。先测基线，后谈优化。任何百分比都必须注明分母和评测条件。

## 12. 面试时我要讲清楚的三个故事

1. **记忆如何保持可信**：为什么保存原文；明确更正如何影响事实和索引；为什么不盲信模型推测。
2. **Agent 如何推进多步任务**：查人、澄清、获得 ID、查记录、组织建议；失败和确认如何处理。
3. **关系数据如何建模**：User 与 Person 的区别；各自维护的联系人为何可以重复；亲属查询为何不能取混合图的最短路径。

展示个人项目的真实实现、模拟数据评测与实际测试结果。历史文档中的“100% 称谓覆盖”“固定毫秒级”“80% 规则命中”等没有测量依据的表述，不作为本轮结论。
