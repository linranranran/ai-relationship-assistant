## 一、为什么要做这个项目

### 核心痛点

1. **不知道该怎么称呼亲戚**：过节见到某个亲戚，不知道叫什么，只能一个劲喊叔叔阿姨。想用图数据库 + RAG 检索，让 LLM 告诉你"这是你三叔"、"这是你四舅"。

2. **记不住人名**：别人需要说很多次才能记住。想用人脸识别拍照匹配，然后从关系图谱中查出对方是谁、什么关系、有什么爱好。

3. **销售场景的延伸价值**：帮助销售人员建立客户关系网络，精准知道客户的喜好、性格，进行针对性服务。

### 项目定位

- **B 类：可用的个人工具** — 自己 + 身边几个人真的会用，有基本的可用性和稳定性
- **业余时间慢慢做，不设 deadline**，享受过程
- **写到简历和 GitHub 上**，体现从 0 到 1 的产品能力

## 二、分阶段规划

## 三、技术选型决策

| 决策项 | 选择 | 原因 |
|--------|------|------|
| 后端语言 | Python | 已学 LangChain/LlamaIndex/LangGraph，Python 生态最熟 |
| AI 编排 | LangGraph | 多步推理 + Tool Calling 的理想框架 |
| 图数据库 | Neo4j Community | 关系网络天然是图结构，Cypher 查询路径遍历极其直观 |
| 向量数据库 | ChromaDB | 轻量、嵌入进程、2核4G 服务器够用 |
| LLM API | DeepSeek / OpenAI 兼容 | 省心效果好，中文能力强 |
| 后端框架 | FastAPI | 轻量、高性能、自动生成 API 文档 |
| 前端 | 纯 Web 响应式 | 一套代码，电脑端管理 + 手机端查询 |
| 部署 | 自备 2核4G 云服务器 | Docker Compose 一键部署 |

### 为什么没选其他方案

- **MySQL**：关系型数据库做多层递归查询（"我→爸爸→爸爸的弟弟→他的儿子"）SQL 会极其痛苦
- **Milvus**：分布式向量数据库，需要至少 4G 内存，2核4G 服务器跑不动
- **微信小程序**：手机端场景简单（搜索+查询），不需要推送/原生能力，Web 响应式足够了
- **本地模型**：优先用云端 API，效果好、省心

## 四、架构设计

### 核心洞察：整个系统 = 一个 Agent

用户只需要像跟人说话一样告诉系统，Agent 自己判断意图、提取信息、调用工具、返回结果。

```
用户输入一句话
    │
    ▼
┌─────────────────────────────────────┐
│              Agent（大脑）            │
│  1. 意图分类：他想做什么？             │
│  2. 信息提取：提到了哪些人物和属性？    │
│  3. 任务规划：需要调用哪些 Tool？      │
│  4. 执行：按顺序调用 Tool             │
│  5. 生成回复：用自然语言告诉用户结果    │
└─────────────────────────────────────┘
        │ 调用
        ▼
┌─────────────────────────────────────┐
│             Tool 层（12 个工具）       │
│  add_person    update_person         │
│  delete_person find_person           │
│  add_relation  update_relation       │
│  delete_relation query_relation_path │
│  get_kinship_title search_by_semantic│
│  get_person_detail list_relations    │
└─────────────────────────────────────┘
        │ 操作
        ▼
┌─────────────────────────────────────┐
│      Neo4j（图）  +  ChromaDB（向量） │
└─────────────────────────────────────┘
```

### Agent 的 12 个意图

| 意图 | 示例输入 |
|------|---------|
| ADD_PERSON | "今天见的张三，李四的朋友，做金融的" |
| UPDATE_PERSON | "张三其实不喜欢钓鱼，他喜欢高尔夫" |
| DELETE_PERSON | "把王五删了吧，不联系了" |
| ADD_RELATION | "李四是张三是同事" |
| UPDATE_RELATION | "张三其实不是我同事，是我老板" |
| DELETE_RELATION | "我和张三不是朋友了" |
| QUERY_PERSON | "张三是谁？" |
| QUERY_KINSHIP | "张三我应该叫什么？" |
| SEMANTIC_SEARCH | "谁喜欢钓鱼？" |
| LIST_RELATIONS | "张三认识哪些人？" |
| CHITCHAT | "你好" |
| UNCLEAR | 意图不明，需要追问 |

## 五、数据模型

### Neo4j

```cypher
-- 人物节点
(:Person {
    id: "p_001",
    name: "张三",
    gender: "男",
    birth_year: 1965,
    occupation: "金融",
    education: "清华大学",
    hobbies: ["钓鱼", "茅台"],
    personality: "开朗",
    tags: [],
    owner: "user_alex",
    created_at: datetime()
})

-- 关系边
(:Person)-[:RELATION {
    id: "r_001",
    type: "父亲",
    owner: "user_alex",
    through: null,
    note: "我爸",
    created_at: datetime()
}]->(:Person)
```

### ChromaDB

- 每个人物一条向量（属性文本的 embedding）
- metadata 中存 `person_id` 和 `owner_id`，用于过滤
- 查询时 `where={"owner_id": current_user}` 实现数据隔离

### 多用户隔离

- **一个图数据库 + owner 属性标记**
- 每条关系边带 `owner` 属性
- 查询时自动过滤：`WHERE edge.owner = $current_user`
- 人物属性可共享（如"张三清华毕业"），私密备注不可共享

## 六、录入体验设计

> 核心原则：**录入的摩擦力必须低于用户忘记这件事的代价。**

### 分层录入

| 层级 | 时机 | 内容 | 耗时 |
|------|------|------|------|
| 第一层 | 见面后 | 姓名 + 关系 | 30 秒 |
| 第二层 | 有空时 | 爱好、职业、性格等 | 1-2 分钟 |
| 第三层 | 自然获取 | 微信头像、合照裁剪 | 零额外操作 |

### 智能录入方式

- **语音备忘录**：说 15 秒，AI 自动提取结构化信息
- **LLM 理解模糊输入**："我老婆的同事，姓王，女的，做设计的" → 自动匹配"王芳（你妻子的同事，UI设计师）"
- **重复检测**：录入时自动检查是否已存在同名人物

## 七、跨用户实体去重策略

> 核心原则：**宁可多存一个重复节点，也不要错误合并。**

### 三层策略

1. **默认不合并**（MVP）：每个用户的数据完全独立
2. **显式关联**（用户手动）：用户发现重复时，手动关联两个节点
3. **LLM 辅助建议**（未来）：系统扫描建议可能的重复，用户确认

## 八、性能评估

### Neo4j 图遍历性能

- 图遍历用"无索引邻接"（指针跳转），每一步 O(1)
- 查询"我→三叔"（3 跳）：始终毫秒级，与总数据量无关
- 单用户 500 人以内，100 个用户，2万节点：**完全够用**

### 2核4G 服务器容量预估

| 用户数 | 总节点 | 能否撑住 |
|--------|--------|---------|
| 10 | 2,000 | ✅ 轻松 |
| 100 | 20,000 | ✅ 没问题 |
| 1,000 | 200,000 | ⚠️ 需要优化 |
| 10,000 | 2,000,000 | ❌ 需要升级 |

## 九、中国亲属称谓方案

### 策略：规则库（80%） + LLM 兜底（20%）

- **规则库**：内置中国亲属称谓规则（父亲/母亲/兄弟姐妹/父系/母系/配偶）
- **年龄排序**：根据排行添加"大"、"二"、"三"、"小"前缀
- **LLM 兜底**：复杂关系（"奶奶的妹妹的丈夫的外甥"）交给 LLM 推理

### 称谓推导流程

```
用户输入"张三"
    → Neo4j 查路径：我 → 父亲 → 张三（父亲的弟弟）
    → 规则库匹配："父亲的弟弟" → "叔叔"
    → 年龄排序：排行第三 → "三叔"
    → 返回："你应该叫张三 **三叔**"
```

## 十、人脸识别（第二版）技术路径

| 卡点 | 方案 |
|------|------|
| 提取人脸信息 | InsightFace（ArcFace 模型），输出 512 维向量 |
| 数据格式 | 512 个 float32 的数组 |
| 存储 | 向量存 ChromaDB，原图存文件系统 |
| 匹配 | 余弦相似度检索，阈值 0.6，返回 Top-3 |
